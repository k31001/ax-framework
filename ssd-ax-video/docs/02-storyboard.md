## 4. 사례 구간의 화면 문법

S5의 일곱 씬은 같은 구성을 쓴다. 보는 사람이 두 번째 단계부터는 읽는 법을 알고 있게 한다.

- **요구사항 카드.** REQ-QOS-07 카드가 화면 위쪽의 7단계 표시를 따라 이동한다. 단계가 끝날 때마다 그 단계의 기록이 카드에 하나씩 붙는다. 카드는 Jira 이슈다: 제목 옆에 `JIRA REQ-207` 이 있고(`REQ-QOS-07` 은 요구사항 ID, `REQ-207` 은 Jira 키), 기록이 Jira의 링크된 이슈이면 이름 앞에 그 키가 붙는다(interface 계약 `FEAT-341`, 검증 기록 `VER-620`, 구동 기록 `VER-588`. 나머지 단계는 이름만). 키와 이름은 `05-jira-traceability.md` 를 따른다.
- **두 줄 구성.** 화면을 "에이전트" 줄과 "사람" 줄로 나눈다. 일이 일어나는 순서대로 각 줄에 항목이 나타나 흐름도가 완성된다. 누가 무엇을 하는지가 한눈에 보인다.
- **현재 → 전환 후.** 단계가 시작되면 "현재" 한 줄이 먼저 나오고, 흐려지면서 "전환 후" 흐름으로 바뀐다.
- **배경 문구.** S5-2와 S5-3에만 있다. 흐름도가 그려지기 전에 본문 위쪽에 한 줄이 크게 나오고(`CONTEXT` 라벨), 그 아래 본문 전체를 그림이 쓴다. 다음 항목이 나오기 전에 물러난다.
- **문제와 해결.** 문제는 경고색 표식으로 흐름 중간에 나타나고, 해결되면 표식이 풀린다.

### S5-2 아키텍처 설계 (19초)

| 구분 | 자막 |
|---|---|
| 배경 | 요구사항 급변 → 구조 재설계 |
| 현재 | RTL 먼저, 구조 문제는 emulation에서 발견 |
| 에이전트 | 목적별 모델 · 수백 구성 여러 관점에서 탐색 |
| 사람 | 선택: 오류 복구 제어를 FW에서 HW로 |
| 문제 | 구조 검증: GC 중 P99.99 초과 |
| 해결 | host read 우선 큐 추가 · RTL 작성 전 발견 |

화면은 문장마다 한 번 바뀐다.

1. 배경. 왼쪽에 이전 세대와 이번 과제의 표(NAND: TLC → 차세대 QLC, 용량: 30.72 TB → 122.88 TB · 4배, 전력 한도: 25 W → 25 W · 그대로. 예시). 오른쪽에 이전 구조(FW 순차 제어 아래 NAND interface → LDPC decoder). FW 왕복이 되풀이되면서 P99.99 막대가 기준 2 ms를 넘어 3.41 ms(예시)에 닿고, 구조의 테두리가 붉은 점선으로 바뀐다.
2. 현재. "RTL 먼저"의 순서 `구조 → RTL → 블록 검증 → emulation` 이 차례로 켜진다. RTL과 블록 검증에는 통과 표시가 붙고, emulation에서야 붉은 깃발 "P99.99 초과"가 선다. 붉은 점선이 맨 앞의 구조로 되돌아간다("구조부터 재작업").
3. 에이전트. 위쪽에 "구조 기술"(`rcv.arch.yaml`) 하나에서 목적별 모델 넷(지연 · 전력, 면적, 기능, formal)이 갈라져 나온다. 그 아래 지연·면적 좌표에 후보 점 수백 개가 찍히고 Pareto 경계가 그려진다. 아래쪽에 여섯 관점(지연 꼬리, 전력, 면적, FW 복잡도, 검증 가능성, 재사용)이 차례로 켜진다.
4. 사람. Pareto 경계에서 하나를 고른다(호박색 고리).
5. 문제와 해결. 목적별 모델과 관점이 물러나고 고른 구조의 상세도가 열린다. GC read와 host read가 soft decoder 앞에 줄을 서고 지연 막대가 기준선을 넘는다. 우선 큐가 생기면서 host read가 앞으로 나온다.

"현재"의 이전 문구(소수 후보, 회의로 결정)는 뺐다. 회의로 고르는 것 자체보다, 고른 구조를 RTL로 먼저 옮기는 순서가 이 씬의 대비다.

### S5-3 IP 설계 · PPA (17초)

| 구분 | 자막 |
|---|---|
| 현재 | register는 SystemRDL, 동작 규약은 API 문서 |
| 배경 | 블록도 한 장 → 블록별 예산 · interface 계약 |
| 사람 | 동작 규약을 실행 가능한 계약으로 정의 |
| 에이전트 | 계약 기반 RTL 생성 · commit마다 PPA 추정 |
| 문제 → 해결 | ECC 블록 면적 초과 → 축소안 · 구조 모델로 지연 재확인 |
| 강조 | 지키는 방법은 설계자의 결정 |
| 원칙 표식 | **스펙 원본화** |

화면은 문장마다 한 번 바뀐다.

1. 배경. "현재"가 머리 쪽으로 물러난 뒤, RTL 설계자가 받는 것이 본문 전체에 놓인다. 왼쪽의 "블록도 한 장"은 점선으로 흐려지고 그 아래에 받는 사람 "RTL 설계자"(호박색). 오른쪽 위는 `01 블록별 지연 예산 (예시)`: 기준 2 ms를 꼬리 경로의 구간으로 나눈 막대(host · FTL 0.10, 첫 read 0.35, HW retry 0.51, soft read 0.30, soft 큐 0.15, soft decode 0.25, 빗금 여유 0.12)와 판정선 1.78 ms. 오른쪽 아래는 `02 interface 계약`(`HSI-RCV-010`): "order host 먼저 · GC는 host 4건당 1건 이상", "bound 모든 요청은 성공 또는 실패로 한 번 종료".
2. 사람, 에이전트. API 문서의 문장이 계약으로 바뀌고, 계약에서 RTL, C++ header, assertion이 갈라져 나온다.
3. 문제와 해결. Commit이 쌓일 때마다 면적 막대가 갱신되다가 예산선을 넘고, 화살표가 S5-2의 구조 모델로 되돌아갔다 온다.
4. 강조. 원칙 띠 자리에 호박색 꺾쇠 상자 "지키는 방법은 설계자의 결정". 옆의 작은 상태도가 점선(구조가 준 출발점)에서 호박색 실선(설계자의 결정)으로 바뀐다. 원칙 표식이 나오기 전에 물러난다.

### S5-4 시뮬레이션 검증 (18초)

| 구분 | 자막 |
|---|---|
| 현재 | 실패 수백 건, 원인 분석은 수작업 |
| 사람 | 통과 기준 정의 · reference model 소유 |
| 에이전트 | testplan · testbench 생성 |
| 문제 | 야간 regression 실패 312건 |
| 에이전트 | 원인 4개로 분류 · 원인 가설: FSM의 완료 신호 누락 |
| 사람 | 가설 확인 · 수정 승인 |
| 해결 | assertion 추가 · 전체 regression 재확인 |
| 원칙 표식 | **폐루프 자동화** · 동일 모델 디버깅 통과율 44% → 94% (NVIDIA 자체 평가, 2026) |

화면: 붉은 점 312개가 네 묶음으로 모인다. 한 묶음이 열리면 복구 요청과 완료 신호가 같은 cycle에 겹치는 파형이 보인다. 원인 가설 항목의 테두리에 Jira 버그 초안의 키 `JIRA BUG-2268` 과 `ai-authored` 가 붙는다(자막 문구는 그대로). 사람이 승인하면 묶음이 풀린다.

### S5-5 Emulation · FPGA (16초)

| 구분 | 자막 |
|---|---|
| 현재 | RTL과 FW의 첫 통합은 FPGA · emulator 준비 이후 |
| 에이전트 | 가상 플랫폼에서 선행 통합, 이후 매일 RTL + FW 구동 |
| 문제 | 장시간 부하 중 command timeout |
| 에이전트 | 파형 · FW trace 교차 분석 · 원인 가설: interrupt 1건 유실 |
| 사람 | HW · FW 공동 결정: 완료 전달을 큐 방식으로, 계약 개정 |

화면: HW 파형과 FW trace가 위아래로 놓이고 같은 시점에 세로선이 그어진다. 완료 신호 두 개가 비트 하나에 겹쳐 하나가 사라진다. 비트가 큐로 바뀌면 둘 다 전달된다.

### S5-6 FW 개발 (10초)

| 구분 | 자막 |
|---|---|
| 현재 | API 문서 해석 후 driver 수작업 구현 |
| 사람 | 불변식 정의: 정정 실패 데이터 반환 금지 |
| 에이전트 | 가상 플랫폼 · 보드에서 빌드 · 실행 · 수정 반복 |
| 사람 | 실제 NAND로 read retry table 승인 |

화면: S5-5에서 개정된 계약이 FW 쪽으로 넘어와 변경안이 된다. 빌드 → 실행 → 수정의 원이 가상 칩 위에서 돈다.

### S5-7 제품 테스트 · 퀄 (20초)

| 구분 | 자막 |
