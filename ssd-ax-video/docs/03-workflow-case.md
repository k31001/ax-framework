# 사례로 보는 워크플로: 요구사항 하나의 여정

> 상태: 승인 대기 초안 2판 (2026-11-10). 설계·검증 관점과 FW·테스트·퀄 관점의 검토를 반영했다.
> 이 문서는 `01-strategy.md` 6장의 7단계를 하나의 구체 사례로 풀어 쓴 것이다. 영상 S4~S5의 원본이다.

## 0. 읽는 법

- **가상 사례다.** 과제, 요구사항 ID, 수치(2 ms, 312건 등)는 흐름을 보여 주기 위한 예시다. 실제 과제 값이 아니다.
- **주체를 구분한다.** 각 단계의 일을 `에이전트`가 하는 일과 `사람`이 하는 일로 나눠 적었다.
- **"전환 후"는 지향점이다.** 단계마다 공개 근거가 어디까지 있는지는 10장에 따로 정리했다.
- **"현재 방식"은 업계 일반론이다.** 팀이 이미 다르게 하고 있는 부분은 고쳐야 한다. 확인이 필요한 곳은 11장에 모았다.
- **범위.** 합성 이후의 backend, DFT, tape-out, silicon bring-up은 다루지 않는다. 6장과 7장은 순서가 아니라 병행이다.

## 1. 사례 설정

**과제.** 차세대 데이터센터 SSD 컨트롤러 SoC. 신세대 QLC NAND를 지원해야 한다.

**따라갈 요구사항.** 이 문서는 요구사항 하나가 스펙에서 퀄까지 가는 길을 따라간다.

| 항목 | 내용 |
|---|---|
| ID | REQ-QOS-07 |
| 요구 | 수명 말기 NAND 조건에서도 read 지연 보장 |
| 수용 기준 (예시) | 혼합 부하에서 P99.99 read latency ≤ 2 ms |
| 출처 | 고객 요구서 |

수치는 예시지만 형태는 실제와 같다. 공개된 OCP Datacenter NVMe SSD Specification v2.5의 20장에는 혼합 워크로드별 P99.99 read 지연 목표가 있고, 대부분 2,000~5,000 µs다.

**왜 이 요구사항인가.** 혼합 부하에서 read 지연의 꼬리는 평소에도 생긴다. Read가 같은 die의 program·erase나 garbage collection과 부딪힐 때다. 이 부분은 스케줄링과 suspend로 관리한다고 전제한다.

NAND가 수명 말기에 가까워지면 여기에 오류 복구가 더해진다. 한 번에 정정되지 않는 read가 늘고, 그런 read는 read retry, 그래도 안 되면 soft decoding, 마지막으로 die 간 parity 복구로 단계가 깊어진다. 단계가 깊어질수록 지연이 길어진다. 수명 말기 조건은 쓰기·지우기 횟수가 한도에 이르고, 오래 방치되고, 쓸 때와 읽을 때의 온도가 다른 경우의 조합이다.

그래서 이 요구사항 하나에 ECC, NAND interface, FW의 read 오류 복구, 제품 신뢰성 시험, 퀄이 모두 걸린다. 한 팀이 풀 수 없고 전 단계가 이어져야 풀린다.

## 2. 요구사항 취합·분석

**입력.** 고객 요구서 개정판, 신세대 QLC NAND 스펙과 초기 평가 데이터, 표준(NVMe, JESD218).

**현재 방식.** 담당자가 문서를 읽고 엑셀에 요구사항을 정리한다. 지연 요구와 NAND 오류율 사이의 충돌은 문서만 봐서는 드러나지 않는다. NAND 평가가 진행된 뒤, 구조가 이미 정해진 시점에 발견된다.

**전환 후 흐름.**

| 순서 | 주체 | 하는 일 |
|---|---|---|
| 1 | 에이전트 | 문서를 조항 단위로 추출해 요구사항 그래프에 등록. 각 요구사항에 출처 조항을 연결 |
| 2 | 에이전트 | 기존 요구사항, 이전 과제의 실측 데이터, NAND 초기 평가 데이터와 대조해 충돌 위험 후보를 보고: "신세대 QLC의 수명 말기 오류율에서는 soft decoding 빈도가 올라 REQ-QOS-07을 위협. 근거: 이전 과제의 read retry 발생률" |
| 3 | 에이전트 | 모호한 조항을 질문으로 올림: "혼합 부하의 read/write 비율과 측정 구간이 고객 요구서에 없음" |
| 4 | 사람 | 고객과 모호한 조항을 확정. 충돌의 우선순위를 결정: "지연 보장 우선, 면적 증가는 한도 내 허용" |
| 5 | 사람 | 수용 기준을 확정: 측정 조건, 판정 방법, 통과 기준 |

**산출물.** 요구사항 카드. ID, 출처 조항, 수용 기준, 영향 블록(ECC, NAND interface, FW read 경로)이 연결돼 있다. 이후 모든 단계의 산출물과 기록이 이 카드에 붙는다.

## 3. 아키텍처 설계와 구조 검증

**입력.** 요구사항 카드와 수용 기준, NAND 오류 특성, 호스트 워크로드 trace, 이전 과제의 실측 데이터.

**현재 방식.** 아키텍트가 기존 성능 모델과 경험으로 두세 안을 만들고 회의에서 고른다. 모델을 새 NAND와 새 구조에 맞게 고치고 보정하는 비용이 커서 후보를 많이 보지 못하고, P99.99 같은 꼬리 지표는 초기에 거의 보지 못한다. HW/FW 분담은 초기에 정하고 다시 평가하지 않는다.

**전환 후 흐름.**

| 순서 | 주체 | 하는 일 |
|---|---|---|
| 1 | 사람 | 탐색의 목표와 제약을 설정: 지연 꼬리 최소화, 면적·전력 한도 |
| 2 | 사람, 에이전트 | 성능 모델과 NAND 오류 모델을 이전 과제의 실측(지연 분포, read retry 발생률)으로 보정하고, 모델을 믿을 수 있는 범위를 기록 |
| 3 | 에이전트 | 수백 개 구성을 탐색. 변수는 decoder 병렬도, soft decoder 수, 오류 복구 제어의 HW/FW 분담, 버퍼 크기 |
| 4 | 에이전트 | 지연·면적·전력의 Pareto 후보와 각 후보의 근거를 보고 |
| 5 | 사람 | 후보 중 하나를 선택하고 이유를 결정 기록으로 남김: "오류 복구 제어를 FW에서 HW로 옮기고 soft decoder 전용 경로를 둔다" |
| 6 | 에이전트 | 선택한 구조의 모델 위에서 REQ-QOS-07의 수용 기준 시나리오를 실행 |

**문제와 해결.** 구조 검증에서 문제가 나왔다. Garbage collection이 열화된 block을 읽으면 soft decoding 요청이 한꺼번에 몰린다. 이때 host read의 복구가 그 뒤에 줄을 서서 P99.99가 기준을 넘는다. 에이전트가 host read 우선 큐를 추가하고 GC의 최소 처리량을 보장하는 수정안을 내고, 다시 실행해 통과를 확인한다. 사람이 수정안을 승인한다.

이런 문제는 현재 방식에서는 emulation이나 제품 테스트 단계에서 나온다. 전환 후에는 모델이 이 경쟁을 표현하는 한 RTL을 쓰기 전에 나온다. NAND 평가 데이터가 갱신되면 다시 돌린다.

**산출물.** 실행 가능한 구조 모델, 결정 기록, 블록별 예산(지연·면적·전력)과 블록별 수용 기준, HW/SW interface 초안. 모두 요구사항 카드에 연결된다.

## 4. IP 설계·조합과 PPA 최적화

**입력.** 검증된 구조 모델, 블록별 예산, HW/SW interface 스펙.

**현재 방식.** 설계자가 구조 문서를 해석해 RTL을 쓴다. Register의 주소와 field는 생성 스크립트로 맞추더라도, interrupt를 지우는 규칙이나 접근 순서 같은 동작 규약은 문서 서술로 남아 HW와 FW가 따로 해석한다. PPA는 후반에 합성 결과로 확인한다.

**전환 후 흐름.**

| 순서 | 주체 | 하는 일 |
|---|---|---|
| 1 | 사람 | 블록 사이의 interface 계약과 블록별 수용 기준을 정의. 동작 규약까지 HW/SW interface 스펙에 넣음 |
| 2 | 에이전트 | Interface 스펙에서 register RTL, FW 헤더, 검증용 register model을 함께 생성 |
| 3 | 에이전트, 사람 | 에이전트가 새 블록의 microarchitecture 안(FSM, datapath, clock·reset 구분)을 내고 사람이 확정 |
| 4 | 에이전트 | 기존 LDPC decoder IP를 구조 모델의 구성대로 설정. 새로 필요한 오류 복구 제어 블록과 우선 큐의 RTL을 생성하고 lint·CDC·sim·formal을 돌려 스스로 수정 |
| 5 | 에이전트 | Commit마다 합성을 돌려 면적·timing·전력을 예산과 비교해 표시 |
| 6 | 사람 | 생성된 RTL의 구조와 interface를 검토하고 승인. Timing·CDC 예외를 판단 |

**문제와 해결.** 합성해 보니 soft decoder 전용 경로를 넣은 ECC 블록이 면적 예산을 넘는다. 에이전트가 soft decoder 수를 줄이고 우선 큐로 보완하는 안을 내고, 이 구성에서도 P99.99가 기준 안인지 구조 모델로 다시 확인한다. 사람이 승인한다.

PPA 결과가 구조 결정으로 되돌아가는 길이 열려 있다는 점이 현재 방식과 다르다.

**산출물.** RTL, 동작 규약까지 담은 interface 스펙, commit별 PPA 기록.

## 5. IP·SoC 시뮬레이션 검증

**입력.** 요구사항 카드에서 내려온 블록별 수용 기준과 지연 예산, RTL, 사람이 소유한 reference model.

**현재 방식.** 검증 엔지니어가 스펙을 읽고 testplan, testbench, assertion을 차례로 손으로 만든다. 야간 regression의 실패는 error message 기준으로 스크립트가 1차로 묶지만, 같은 원인이 다른 message로 나오는 경우는 사람이 가려야 한다. 묶음마다 testbench 문제인지 RTL 문제인지 가르는 데 시간이 든다.

**전환 후 흐름.**

| 순서 | 주체 | 하는 일 |
|---|---|---|
| 1 | 사람 | 검증 의도와 통과 기준을 정의. Reference model을 설계와 독립된 경로로 유지 |
| 2 | 에이전트 | 블록별 수용 기준에서 testplan 항목을 파생하고 testbench와 sequence를 생성. 예: 복구 요청부터 완료까지의 최대 지연, host read가 GC read보다 먼저 처리될 것, 모든 복구 요청이 성공 또는 실패로 끝날 것 |
| 3 | 사람 | 생성된 testbench와 assertion을 검토 |
| 4 | 에이전트 | Regression을 돌리고 coverage의 빈 곳을 분석해 테스트를 추가 |
| 5 | 에이전트 | 실패를 원인별로 묶고, 묶음마다 대표 seed를 파형과 함께 재실행해 원인 가설을 작성 |
| 6 | 사람 | 가설과 수정안을 검토하고 승인 |

P99.99 자체는 시뮬레이션으로 판정하지 않는다. 구조 모델(3장), 실제 FW를 올린 emulation과 FPGA(6장), 제품 테스트(8장)에서 판정한다. 새 블록을 SoC에 연결한 뒤에는 connectivity·CDC·reset 검사와 SoC 수준 테스트가 이어진다.

**문제와 해결.** 야간 regression에서 312건이 실패했다.

1. 에이전트가 312건을 원인 4개로 묶는다.
2. 그중 하나의 원인 가설: "오류 복구 요청과 decode 완료 신호가 같은 cycle에 오면 제어 FSM이 완료를 놓치고 해당 command가 멈춘다."
3. 에이전트가 대표 seed, 파형 구간, 수정 후보, 재현 테스트를 묶어 티켓으로 올린다.
4. 설계자가 가설을 확인하고 수정을 승인한다.
5. 실패했던 묶음과 영향받는 테스트를 먼저 돌려 수정을 확인하고, 그날 밤 전체 regression으로 부작용을 확인한다.
6. 이 경우를 잡는 assertion(formal property 포함)과 coverage 항목이 testplan에 추가된다.

**검증의 독립성.** 이 bug는 4장에서 설계 에이전트가 돌린 검사를 통과했다. 설계 쪽 검사는 설계와 같은 해석을 공유하기 때문이다. 그래서 reference model과 통과 기준은 사람이 소유하고, 검증 품질은 에이전트의 자기 보고가 아니라 심어 둔 bug의 검출률로 잰다.

**산출물.** 요구사항에 연결된 testplan, coverage 결과, 원인과 수정이 기록된 bug 묶음.

## 6. Emulator·FPGA와 HW/SW co-verification

**입력.** 최신 RTL, 실제 FW, 긴 혼합 부하. 플랫폼은 둘이다. Emulator는 read 전압에 따라 오류 수가 달라지는 수명 말기 NAND 모델을 쓰고 파형을 볼 수 있다. FPGA는 실제 NAND를 붙여 장시간 부하를 돌린다.

**현재 방식.** 최신 RTL과 최신 FW가 만나는 것은 RTL이 안정된 뒤다. 실패는 긴 실행 끝에 나오고, 재현하려면 다시 장비 순서를 기다린다. HW 팀과 FW 팀이 각자의 trace를 들고 원인이 어느 쪽인지 다툰다.

**전환 후 흐름.**

| 순서 | 주체 | 하는 일 |
|---|---|---|
| 1 | 에이전트 | 매일(emulator 기준) 최신 RTL과 최신 FW를 올려 부팅과 I/O 시나리오를 실행 |
| 2 | 에이전트 | 실패가 나면 HW 파형과 FW trace를 같은 시간축에 놓고 분석해 원인 가설을 작성 |
| 3 | 에이전트 | 실패를 시뮬레이션에서 돌릴 수 있는 작은 재현 케이스로 줄임 |
| 4 | 사람 | HW와 FW 담당이 함께 원인을 확인하고 interface 변경을 결정 |

**문제와 해결.** 장시간 혼합 부하 중 command timeout이 났다.

1. 에이전트의 원인 가설: "복구 완료가 짧은 간격으로 두 번 오면, FW가 status를 읽고 지우기 전에 두 번째 완료가 같은 비트에 겹쳐 한 건이 사라진다."
2. IP 시뮬레이션에서는 FW 역할의 sequence가 status를 바로 지워서 드러나지 않았다.
3. 에이전트가 이를 작은 시뮬레이션 재현 케이스로 줄인다.
4. HW와 FW 담당이 HW/SW interface 스펙을 고친다. 완료를 비트 하나가 아니라 큐로 전달하고, 큐가 찼을 때의 동작도 정한다.
5. 스펙에서 register 정의와 FW 헤더가 다시 생성된다. 큐 로직의 RTL과 FW의 완료 처리 코드는 에이전트가 수정안을 내고 HW와 FW 담당이 검토하며, 4~5장의 생성·검증 루프를 다시 거친다.
6. 재현 케이스가 IP regression에 편입된다.

4장에서 말한 "문서로 남은 동작 규약"이 바로 이런 bug의 자리다. 원인을 따지는 대상이 사람에서 스펙으로 바뀐다.

**산출물.** 일일 부팅·I/O 결과, 재현 케이스, 개정된 interface 스펙.

**주의.** 매일 돌리고 실패마다 다시 돌리면 장비 수요는 늘어난다. 장비 용량과 실행 우선순위에 예산을 둬야 한다.

## 7. SoC 구동 SW/FW 개발

**입력.** HW/SW interface 스펙, NAND 특성 데이터, 가상 플랫폼(FW가 그대로 실행되는 SoC·NAND 모델. 구조 모델과 interface 스펙에서 파생하고 FW 팀이 유지), 실제 NAND를 붙인 보드.

**현재 방식.** Register 정의는 생성되더라도 초기화 순서, 사용 조건, errata는 문서와 구두로 전해져 FW가 손으로 구현한다. HW 변경은 늦게 전해진다. 보드에 올려 로그를 확인하는 디버그 반복이 사람 손에 묶여 있고 보드 순서를 기다린다.

**전환 후 흐름.**

| 순서 | 주체 | 하는 일 |
|---|---|---|
| 1 | 에이전트 | Interface 스펙에서 driver 골격과 헤더를 생성. 스펙이 바뀌면 FW 변경안을 올림 |
| 2 | 사람 | Read 오류 복구 정책의 목표와 불변식을 정의: "정정에 실패한 데이터는 host에 반환하지 않고 오류로 응답한다", "ECC 정정과 데이터 경로 보호 검사를 모두 통과한 데이터만 반환한다", "복구 단계별 지연 상한과 전체 복구 시간 상한" |
| 3 | 에이전트 | 가상 플랫폼과 보드에서 빌드, 실행, 로그 확인, 수정을 반복 |
| 4 | 에이전트 | NAND 특성 데이터로 read retry table 후보를 탐색하고, 탐색에 쓰지 않은 lot·조건의 데이터로 후보를 평가 |
| 5 | 사람 | NAND 특성 담당이 실제 NAND 시료에서 후보를 확인하고 table을 승인. 특성 데이터가 덮는 lot·조건 범위를 기록 |
| 6 | 사람 | 코드를 검토하고 승인. 데이터 무결성 경로는 사람이 직접 확인 |

**산출물.** Driver, 오류 복구 FW, read retry table, 불변식 테스트. 불변식의 판정 기준과 host 쪽 data compare는 사람이 소유하고 FW를 만든 에이전트와 분리한다.

## 8. 제품 테스트와 퀄 승인

**입력.** 요구사항 카드의 수용 기준, 시제품, 테스트 로그, 지금까지 쌓인 추적 기록.

**현재 방식.** 테스트 케이스를 사람이 설계한다. 불량 로그는 소수 전문가가 읽는다. 퀄 막바지에 결과를 모아 고객 양식으로 리포트를 쓴다. 필드 이슈는 다음 과제에 늦게, 비공식적으로 전해진다.

**전환 후 흐름.**

| 순서 | 주체 | 하는 일 |
|---|---|---|
| 1 | 에이전트 | 수용 기준에서 제품 테스트 항목을 파생: 수명 말기 시료의 혼합 부하 지연, 고온 방치를 더한 뒤의 지연, 쓰기와 읽기의 온도 교차, read disturb 누적 후 지연, 여러 NAND lot 반복 |
| 2 | 에이전트 | 실패 로그를 분류하고 기존 불량 지식베이스와 대조해 묶음 후보와 근거 로그 구간을 제시 |
| 3 | 사람 | 개발 단계 시험에서는 묶음 결과를 표본으로 점검하고 신규 후보를 검토. 퀄 시료의 불량은 묶음 여부와 관계없이 전건을 직접 처분 |
| 4 | 에이전트 | 요구사항 카드의 기록으로 퀄 패키지를 조립. 수치마다 원본 로그를 연결 |
| 5 | 사람 | 품질 책임자가 사내 퀄을 판정하고 서명. 고객 퀄은 고객이 승인 |

**문제와 해결.** 고온 방치 후 전원을 넣은 직후 구간에서, 특정 NAND lot의 read 지연이 기준을 넘었다.

1. 에이전트가 실패 로그를 분류해 신규 불량 후보로 올린다.
2. 원인 가설: "이 lot은 방치 후 read 전압 이동이 커서, 맞는 read 전압이 read retry table의 뒤쪽 순서에 있거나 범위 밖이다. Read마다 retry가 여러 번 돌고 일부는 soft decoding까지 내려간다."
3. NAND 담당이 불량 시료의 read 전압 분포를 측정해 가설을 확인한다. 사람이 처분을 정한다: "lot 편차가 NAND 스펙 안이므로 FW에서 받는다." 스펙 밖이었다면 NAND 쪽 조치다.
4. 에이전트가 수정안 셋의 지연 효과와 다른 lot에 대한 부작용을 특성 데이터로 비교해 보고한다: table에 영역 추가와 순서 조정, 한 번 성공한 read 전압을 같은 block 묶음의 다음 read 시작값으로 쓰는 정책, 전원 인가 후 read 전압 재보정. 사람이 고른다.
5. 에이전트가 재시험 범위 초안을 낸다. 다른 lot의 지연 회귀 확인이 들어간다. 무결성 경로 변경에 붙는 고정 재시험 항목은 사람이 정해 둔 것이고 에이전트가 줄일 수 없다.
6. FW와 품질 담당이 수정과 재시험 범위를 승인하고 고객과 합의한다.
7. 재시험에는 수명 말기까지 열화시킨 시료와 방치 시간이 다시 필요하다. 이 시간은 줄지 않는다. 줄어든 것은 원인 가설까지의 시간과 범위 산정이다.
8. 이 lot의 특성이 NAND 오류 모델(3장)과 특성 데이터(7장)에 추가된다.

**추적 기록과 퀄 증빙.** 둘은 다르다. 구조 모델 결과, 시뮬레이션 coverage, 일일 FW 구동 결과는 설계 검증 기록으로 요구사항 카드에 남는다. 퀄 증빙은 퀄 대상 FW·HW·NAND lot의 시료로 얻은 신뢰성 시험과 지연 측정 결과다. 모든 기록에는 구성(FW commit, HW revision, NAND lot)이 붙고, 구성이 바뀌면 해당 기록은 "재확인 필요"로 표시된다. 개발 내내 쌓이는 것은 추적 연결과 시험 자산이고, 퀄 데이터 자체는 최종 구성에서 얻는다.

**다음 과제로.** 양산 후 고객이 제공하기로 합의한 필드 telemetry(복구 단계별 발생 횟수, 지연 임계 초과 기록)는 먼저 현 제품의 FW 개선과 반품 분석에 쓰이고, 다음 과제의 요구사항 후보로도 올라온다. 사람이 채택 여부를 정한다. 2장으로 돌아간다.

| 단계 | 전환 후 요소 | 공개 근거 | 수준 |

| 아키텍처 | 시뮬레이터를 돌리는 설계 공간 탐색 에이전트 | Agentic Architect(2026-04) 등. 대상은 CPU·accelerator | 논문. SSD 컨트롤러 사례는 없음 |
| IP 설계 | Register 스펙에서 RTL·헤더·검증 모델 동시 생성 | Agnisys 등 | 상용 |
| IP 설계 | Spec-to-RTL 에이전트 | Synopsys, Cadence의 2026년 발표 | 평가·early access 단계 |

| 시뮬레이션 검증 | Testplan·testbench 생성과 coverage 수렴 | Synopsys, Cadence, Siemens의 2026년 발표. 독립 실험에서 심어 둔 bug의 21~37% 누락 | Early access·고객 평가 단계 |
| 시뮬레이션 검증 | 실패 묶음, 대표 재실행, 원인 가설 | Samsung의 DVCon U.S. 2026 논문(로그 기반 150건), ChipAgents 기고(2026-10) | 논문과 제품. 원인 가설의 정확도는 공개 수치 없음 |
| Emulation | Emulation 실패를 시뮬레이션 재현 케이스로 축소 | 직접 사례 없음. 인접 사례는 silicon 실패를 emulation에서 재현한 Samsung Semiconductor India Research 논문(방향이 반대, FW 없는 구성) | 제안 |
| Emulation | HW 파형과 FW trace 교차 분석 | 시간축을 맞춘 HW/SW 디버그 뷰는 상용. 에이전트의 원인 가설은 직접 사례 없음 | 기반은 상용, 에이전트는 제안 |
| FW | 닫힌 루프의 FW 에이전트 | Bitcraze(2026-04), Embedder(2025-08). 범용 임베디드, 실제 보드 대상 | 제품과 사례. SSD FW 사례는 없음 |
| FW | 스펙 변경 시 FW 변경안 생성 | 직접 사례 없음 | 제안 |
| FW | 특성 데이터 기반 read retry table 탐색 | Read 전압 예측 연구는 있음. 에이전트가 수행한 사례는 없음 | 제안 |
| 테스트 | 실패 로그 자동 진단 | Google Auto-Diagnose(2026-04). SW 통합 테스트 대상, 정확도 평가 표본 71건 | 타 분야 배포 사례. SSD는 Solidigm의 소개 수준 |
| 테스트 | 기존 불량과 대조해 묶기 | Samsung의 DVCon U.S. 2026 논문(RTL regression 대상) | 논문. 제품 테스트 사례는 없음 |
| 퀄 | 재시험 범위 제안, 퀄 패키지 조립 | 직접 사례 없음. 추적성 툴은 상용 | 제안 |
| 퀄 | 필드 telemetry의 요구사항 환류 | 표준 로그는 있음(OCP Datacenter NVMe SSD spec). 환류 자동화 사례는 없음 | 제안 |

요약하면, 상용 제품이 있는 것은 register 생성과 RTL 단계 PPA 추정이다. Spec-to-RTL과 검증 에이전트는 벤더의 early access·고객 평가 단계이고 수치는 자사 발표다. 2·3·6장의 대부분, 7장의 table 탐색과 스펙 변경의 FW 반영, 8장의 재시험 범위 제안과 필드 환류는 이 전략이 제안하는 부분이다. 단계와 단계를 하나의 요구사항 카드로 잇는 흐름 전체는 공개된 완성 사례가 없다.

## 11. 팀 확인이 필요한 곳

검토에서 "팀 실태에 따라 달라진다"고 지적된 서술이다. 팀 상황과 다르면 해당 장의 "현재 방식"을 고친다.

| 장 | 서술 | 확인할 것 |
|---|---|---|
| 3 | 꼬리 지표를 초기에 거의 보지 못한다 | 팀이 쓰는 성능 모델의 수준과 보정 방식 |
| 4, 7 | 동작 규약, 초기화 순서, errata는 문서와 구두로 전해진다 | Register와 HW/SW interface의 관리 방식 |
| 5 | 1차 묶음은 스크립트, 원인 분석은 사람 | Regression triage의 현재 자동화 수준 |
| 6 | 최신 RTL과 최신 FW는 RTL이 안정된 뒤에 만난다 | Emulator와 FPGA에서 FW를 올리는 시점과 주기 |
| 6 | 대안 사례: HW 복구 엔진이 read 전압을 바꿔 둔 die에 FW가 다음 read를 내보내는 충돌 | 대상 NAND에서 read 전압 변경이 die에 남는 설정인지. 맞다면 interrupt 유실보다 이 요구사항에 더 밀착된 사례다 |
| 8 | 퀄 증빙은 최종 구성의 시료 결과만 인정, 재시험 범위는 고객과 합의 | 사내 퀄과 고객 퀄의 실제 규정 |
