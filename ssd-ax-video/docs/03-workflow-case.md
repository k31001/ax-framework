# 사례로 보는 워크플로: 요구사항 하나의 여정

> 상태: 승인 대기 초안 (2026-11-10)
> 이 문서는 `01-strategy.md` 6장의 7단계를 하나의 구체 사례로 풀어 쓴 것이다. 영상 S4~S5의 원본이다.

## 0. 읽는 법

- **가상 사례다.** 과제, 요구사항 ID, 수치(2 ms, 312건 등)는 흐름을 보여 주기 위한 예시다. 실제 과제 값이 아니다.
- **주체를 구분한다.** 각 단계의 일을 `에이전트`가 하는 일과 `사람`이 하는 일로 나눠 적었다.
- **"전환 후"는 지향점이다.** 단계마다 공개 근거가 어디까지 있는지는 9장에 따로 정리했다.

## 1. 사례 설정

**과제.** 차세대 데이터센터 SSD 컨트롤러 SoC. 신세대 QLC NAND를 지원해야 한다.

**따라갈 요구사항.** 이 문서는 요구사항 하나가 스펙에서 퀄까지 가는 길을 따라간다.

| 항목 | 내용 |
|---|---|
| ID | REQ-QOS-07 |
| 요구 | 수명 말기 NAND 조건에서도 read 지연 보장 |
| 수용 기준 (예시) | 혼합 부하에서 P99.99 read latency ≤ 2 ms |
| 출처 | 고객 요구서 |

**왜 이 요구사항인가.** NAND가 수명 말기에 가까워지면 오류율이 올라간다. 한 번에 정정되지 않는 read가 늘고, 그때마다 read retry와 soft decoding이 추가로 돈다. 이 추가 동작이 read 지연의 꼬리를 만든다. 그래서 이 요구사항 하나에 ECC, NAND interface, FW의 read 오류 복구, 제품 신뢰성 시험, 퀄이 모두 걸린다. 한 팀이 풀 수 없고 전 단계가 이어져야 풀린다.

## 2. 요구사항 취합·분석

**입력.** 고객 요구서 개정판, 신세대 QLC NAND 스펙, 표준(NVMe, JESD218).

**현재 방식.** 담당자가 세 문서를 읽고 엑셀에 요구사항을 정리한다. 지연 요구와 NAND 오류율 사이의 충돌은 문서만 봐서는 드러나지 않는다. NAND 평가 결과가 나온 뒤, 구조가 이미 정해진 시점에 발견된다.

**전환 후 흐름.**

| 순서 | 주체 | 하는 일 |
|---|---|---|
| 1 | 에이전트 | 세 문서를 조항 단위로 추출해 요구사항 그래프에 등록. 각 요구사항에 출처 조항을 연결 |
| 2 | 에이전트 | 기존 요구사항, 이전 과제의 실측 데이터와 대조해 충돌 후보를 보고: "신세대 QLC의 수명 말기 오류율에서는 soft decoding 빈도가 올라 REQ-QOS-07과 충돌. 근거: 이전 과제의 read retry 발생률" |
| 3 | 에이전트 | 모호한 조항을 질문으로 올림: "혼합 부하의 read/write 비율과 측정 구간이 고객 요구서에 없음" |
| 4 | 사람 | 고객과 모호한 조항을 확정. 충돌의 우선순위를 결정: "지연 보장 우선, 면적 증가는 한도 내 허용" |
| 5 | 사람 | 수용 기준을 확정: 측정 조건, 판정 방법, 통과 기준 |

**산출물.** 요구사항 카드. ID, 출처 조항, 수용 기준, 영향 블록(ECC, NAND interface, FW read 경로)이 연결돼 있다. 이후 모든 단계의 산출물과 증빙이 이 카드에 붙는다.

## 3. 아키텍처 설계와 구조 검증

**입력.** 요구사항 카드와 수용 기준, NAND 오류 특성, 호스트 워크로드 trace.

**현재 방식.** 아키텍트가 엑셀 모델과 경험으로 두세 안을 만들고 회의에서 고른다. 모델을 만들고 보정하는 비용이 커서 후보를 많이 보지 못한다. HW/FW 분담은 초기에 정하고 다시 평가하지 않는다.

**전환 후 흐름.**

| 순서 | 주체 | 하는 일 |
|---|---|---|
| 1 | 사람 | 탐색의 목표와 제약을 설정: 지연 꼬리 최소화, 면적·전력 한도 |
| 2 | 에이전트 | 성능 모델, NAND 오류 모델, 워크로드 trace로 수백 개 구성을 탐색. 변수는 decoder 병렬도, soft decoder 수, 오류 복구 제어의 HW/FW 분담, 버퍼 크기 |
| 3 | 에이전트 | 지연·면적·전력의 Pareto 후보와 각 후보의 근거를 보고 |
| 4 | 사람 | 후보 중 하나를 선택하고 이유를 결정 기록으로 남김: "오류 복구 제어를 FW에서 HW로 옮기고 soft decoder 전용 경로를 둔다" |
| 5 | 에이전트 | 선택한 구조의 모델 위에서 REQ-QOS-07의 수용 기준 시나리오를 실행 |

**문제와 해결.** 구조 검증에서 문제가 나왔다. Garbage collection이 동시에 진행되면 GC read와 host read가 soft decoder를 두고 경쟁해 P99.99가 기준을 넘는다. 에이전트가 host read 우선 큐를 추가한 수정안을 내고 다시 실행해 통과를 확인한다. 사람이 수정안을 승인한다.

이 문제는 현재 방식에서는 emulation이나 제품 테스트 단계에서 나온다. 전환 후에는 RTL을 쓰기 전에 나온다.

**산출물.** 실행 가능한 구조 모델, 결정 기록, 블록별 예산(지연·면적·전력), HW/SW interface 초안. 모두 요구사항 카드에 연결된다.

## 4. IP 설계·조합과 PPA 최적화

**입력.** 검증된 구조 모델, 블록별 예산, HW/SW interface 스펙.

**현재 방식.** 설계자가 구조 문서를 해석해 RTL을 쓴다. Register map은 엑셀에서 RTL과 FW 헤더로 각각 손으로 옮겨져 어긋난다. PPA는 후반에 합성 결과로 확인한다.

**전환 후 흐름.**

| 순서 | 주체 | 하는 일 |
|---|---|---|
| 1 | 사람 | 블록 사이의 interface 계약과 블록별 수용 기준을 정의 |
| 2 | 에이전트 | HW/SW interface 스펙에서 register RTL, FW 헤더, 검증용 register model을 함께 생성 |
| 3 | 에이전트 | 기존 LDPC decoder IP를 구조 모델의 구성대로 설정. 새로 필요한 오류 복구 제어 블록과 우선 큐의 RTL을 생성하고 lint·sim·formal을 돌려 스스로 수정 |
| 4 | 에이전트 | Commit마다 합성을 돌려 면적·timing·전력을 예산과 비교해 표시 |
| 5 | 사람 | 생성된 RTL의 구조와 interface를 검토하고 승인 |

**문제와 해결.** Decoder 출력 경로가 timing을 못 맞춘다. 에이전트가 pipeline 1단 추가안을 내고, 늘어난 지연이 예산 안인지 구조 모델로 다시 확인한다. 사람이 승인한다.

**산출물.** RTL, 단일 원본 register map, commit별 PPA 기록.

## 5. IP·SoC 시뮬레이션 검증

**입력.** 요구사항 카드의 수용 기준, RTL, 사람이 소유한 reference model.

**현재 방식.** 검증 엔지니어가 스펙을 읽고 testplan, testbench, assertion을 차례로 손으로 만든다. 아침마다 야간 regression의 실패 로그 수백 건을 분류한다. 같은 원인의 중복을 가려내는 데 시간이 가장 많이 든다.

**전환 후 흐름.**

| 순서 | 주체 | 하는 일 |
|---|---|---|
| 1 | 사람 | 검증 의도와 통과 기준을 정의. Reference model을 설계와 독립된 경로로 유지 |
| 2 | 에이전트 | 수용 기준에서 testplan 항목을 파생하고 testbench와 sequence를 생성 |
| 3 | 에이전트 | Regression을 돌리고 coverage의 빈 곳을 분석해 테스트를 추가 |
| 4 | 에이전트 | 실패를 원인별로 묶고, 묶음마다 대표 seed를 파형과 함께 재실행해 원인 가설을 작성 |
| 5 | 사람 | 가설과 수정안을 검토하고 승인 |

**문제와 해결.** 야간 regression에서 312건이 실패했다.

1. 에이전트가 312건을 원인 4개로 묶는다.
2. 그중 하나의 원인 가설: "오류 복구 요청과 decode 완료 신호가 같은 cycle에 오면 제어 FSM이 완료를 놓치고 해당 command가 멈춘다."
3. 에이전트가 대표 seed, 파형 구간, 수정 후보, 재현 테스트를 묶어 티켓으로 올린다.
4. 설계자가 가설을 확인하고 수정을 승인한다.
5. 영향받는 테스트만 골라 다시 돌린다. 이 경우를 잡는 assertion과 coverage 항목이 testplan에 추가된다.

**검증의 독립성.** 설계와 검증을 같은 에이전트가 같은 해석으로 만들면 같은 오해를 공유한다. 그래서 reference model과 통과 기준은 사람이 소유하고, 검증 품질은 에이전트의 자기 보고가 아니라 심어 둔 bug의 검출률로 잰다.

**산출물.** 요구사항에 연결된 testplan, coverage 결과, 원인과 수정이 기록된 bug 묶음.

## 6. Emulator·FPGA와 HW/SW co-verification

**입력.** 최신 RTL, 실제 FW, 수명 말기 오류를 주입하는 NAND 모델, 긴 혼합 부하.

**현재 방식.** 장비 순서를 기다린다. 실제 FW는 RTL이 안정된 뒤에야 올라간다. 실패는 긴 실행 끝에 나오고, 재현하려면 다시 줄을 선다. HW 팀과 FW 팀이 각자의 trace를 들고 원인이 어느 쪽인지 다툰다.

**전환 후 흐름.**

| 순서 | 주체 | 하는 일 |
|---|---|---|
| 1 | 에이전트 | 매일 최신 RTL과 최신 FW를 올려 부팅과 I/O 시나리오를 실행 |
| 2 | 에이전트 | 실패가 나면 HW 파형과 FW trace를 같은 시간축에 놓고 분석해 원인 가설을 작성 |
| 3 | 에이전트 | 실패를 시뮬레이션에서 돌릴 수 있는 작은 재현 케이스로 줄임 |
| 4 | 사람 | HW와 FW 담당이 함께 원인을 확인하고 interface 변경을 결정 |

**문제와 해결.** 장시간 혼합 부하 중 command timeout이 났다.

1. 에이전트의 원인 가설: "복구 완료 interrupt가 연속으로 오면, FW가 status를 지우는 사이에 다음 완료가 유실된다."
2. 에이전트가 이를 작은 시뮬레이션 재현 케이스로 줄인다.
3. HW와 FW 담당이 HW/SW interface 스펙을 고친다: 완료를 비트 하나가 아니라 큐로 전달.
4. 스펙에서 register RTL과 driver가 함께 다시 생성된다.
5. 재현 케이스가 IP regression에 편입된다.

원인을 따지는 대상이 사람에서 스펙으로 바뀐다.

**산출물.** 일일 부팅·I/O 결과, 재현 케이스, 개정된 interface 스펙.

## 7. SoC 구동 SW/FW 개발

**입력.** HW/SW interface 스펙, 구조 모델, NAND 특성 데이터.

**현재 방식.** FW 엔지니어가 HW 스펙 문서에서 register를 손으로 옮긴다. HW 변경은 늦게 전해진다. 빌드, flash, 로그 확인이 사람 손에 묶여 있고 보드 순서를 기다린다.

**전환 후 흐름.**

| 순서 | 주체 | 하는 일 |
|---|---|---|
| 1 | 에이전트 | Interface 스펙에서 driver 골격과 헤더를 생성. 스펙이 바뀌면 FW 변경안을 자동으로 올림 |
| 2 | 사람 | Read 오류 복구 정책의 목표와 불변식을 정의: "미정정 데이터는 어떤 경우에도 반환하지 않는다", "복구 단계별 지연 상한" |
| 3 | 에이전트 | 가상 플랫폼에서 빌드, 실행, 로그 확인, 수정을 반복 |
| 4 | 에이전트 | NAND 특성 데이터로 read retry table의 후보를 탐색 |
| 5 | 사람 | 코드를 검토하고 승인. 데이터 무결성 경로는 사람이 직접 확인 |

**산출물.** Driver, 오류 복구 FW, 실행 가능한 불변식 테스트, read retry table.

## 8. 제품 테스트와 퀄 승인

**입력.** 요구사항 카드의 수용 기준, 시제품, 테스트 로그, 지금까지 쌓인 증빙.

**현재 방식.** 테스트 케이스를 사람이 설계한다. 불량 로그는 소수 전문가가 읽는다. 퀄 막바지에 결과를 모아 고객 양식으로 리포트를 쓴다. 필드 이슈는 다음 과제에 늦게, 비공식적으로 전해진다.

**전환 후 흐름.**

| 순서 | 주체 | 하는 일 |
|---|---|---|
| 1 | 에이전트 | 수용 기준에서 제품 테스트 항목을 파생: 수명 말기 조건의 지연, 고온 방치 후 read, 전력, 호환성 |
| 2 | 에이전트 | 실패 로그를 분류하고 기존 불량 지식베이스와 대조. 알려진 불량은 기존 건에 묶고 처음 보는 불량만 사람에게 올림 |
| 3 | 사람 | 신규 불량을 검토하고 수정과 재시험 범위를 승인 |
| 4 | 에이전트 | 요구사항 카드에 쌓인 증빙으로 퀄 패키지를 조립. 수치마다 원본 로그를 연결 |
| 5 | 사람 | 퀄을 판정하고 서명 |

**문제와 해결.** 고온 방치 후 특정 NAND lot에서 read 지연이 기준을 넘었다.

1. 에이전트가 실패 로그를 분류하고 기존 불량과 대조해 신규 불량으로 판정한다.
2. 원인 가설: "이 lot은 고온 방치 후 read 전압 이동이 커서 read retry table의 범위를 벗어난다."
3. 에이전트가 table 수정안과 함께, 이 변경이 영향을 주는 시험만 골라 재시험 범위를 제안한다.
4. 사람이 수정과 재시험 범위를 승인한다.

**REQ-QOS-07에 쌓인 증빙.** 구조 모델의 시나리오 결과, 시뮬레이션 coverage, 일일 FW 구동 결과, 신뢰성 시험 데이터. 퀄 막바지에 모으는 것이 아니라 개발 내내 쌓인 것이다.

**다음 과제로.** 양산 후 필드 telemetry(read retry 발생률, 지연 분포)가 다음 과제의 요구사항 후보로 올라오고 사람이 채택 여부를 정한다. 2장으로 돌아간다.

## 9. 역할별 변화

| 역할 | 줄어드는 일 | 늘어나는 일 |
|---|---|---|
| 요구사항·시스템 담당 | 문서 대조, 엑셀 추적표 관리 | 우선순위 결정, 수용 기준 확정, 고객과의 모호성 해소 |
| 아키텍트 | 후보 두세 개의 수작업 모델링 | 목표와 제약 설정, 후보 선택, 결정 기록 |

## 10. 공개 근거 수준

"전환 후"의 각 요소가 공개 자료에서 어디까지 확인되는지 정리했다. 상세 출처는 `research/` 문서에 있다.

| 단계 | 전환 후 요소 | 공개 근거 | 수준 |
|---|---|---|---|
| 요구사항 | 스펙을 그래프로 바꿔 공백·충돌 탐지 | Intel의 스펙 보안 공백 탐지(2026-05), ChipMind(AAAI-26) | 사내 사례 1건과 논문 |
| 아키텍처 | 시뮬레이터를 돌리는 설계 공간 탐색 에이전트 | Agentic Architect(2026-04) 등. 대상은 CPU·accelerator | 논문. SSD 컨트롤러 사례는 없음 |
| IP 설계 | Register 스펙에서 RTL·헤더·검증 모델 동시 생성 | Agnisys 등 상용 툴 | 상용 |
| IP 설계 | Spec-to-RTL 에이전트 | Synopsys, Cadence의 2026년 발표 | 평가·early access 단계 |
| PPA | 자동 파라미터 탐색 | Synopsys DSO.ai, Cadence Cerebrus. Kioxia 적용 사례(2026-04) | 상용 |
| 시뮬레이션 검증 | 실패 묶음, 대표 재실행, 원인 가설 | Samsung의 DVCon U.S. 2026 논문, ChipAgents 기고(2026-10) | 논문과 제품 |
| Emulation | 실패 재현 자동화 | Samsung Semiconductor India Research의 DVCon U.S. 2026 논문 | 논문 |
| Emulation | HW 파형과 FW trace 교차 분석 | 직접 사례 없음 | 제안 |
| FW | 닫힌 루프의 FW 에이전트 | Bitcraze(2026-04), Embedder(2025-08). 범용 임베디드 대상 | 제품과 사례 |
| FW | FW 파라미터 자동 튜닝 | Solidigm의 Athena 소개(2026-01) | 자사 소개, 수치 없음 |
| 테스트 | 실패 로그 자동 진단 | Google Auto-Diagnose(2026-04). SW 통합 테스트 대상 | 대규모 배포. 스토리지 사례는 Solidigm 소개 수준 |
| 퀄 | 개발 내내 누적되는 증빙, 퀄 패키지 자동 조립 | 직접 사례 없음. 추적성 툴은 상용 | 제안 |

요약하면, 4장과 5장의 요소는 제품이 나와 있고, 2·3·6장의 일부와 8장의 증빙 누적은 이 전략이 제안하는 부분이다. 단계와 단계를 하나의 요구사항 카드로 잇는 흐름 전체는 공개된 완성 사례가 없다.
