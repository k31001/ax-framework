# Jira 추적성 모델: 6편 공통 기준

> 상태: 초안 (2026-11-11). 본편과 상세 5편이 같은 Jira 모델을 쓰기 위한 기준 문서다.
> 이슈 키, 번호, 계정 이름, 수치는 모두 예시다. 팀의 실제 Jira는 조회하지 않았다. Cloud인지 Data Center(DC)인지도 모른다. 차이가 나는 곳은 표시했다.

## 1. 한 줄 요약과 원칙

**Jira는 추적과 소통의 기준 시스템이고, 실행 가능한 산출물의 원본은 git이다.**

| | Jira에 산다 | git에 산다 |
|---|---|---|
| 내용 | 이슈 키, 상태, 링크, 담당, 논의(댓글), 승인 기록(전환 이력) | 요구사항 카드의 수용 기준, 계약 YAML, SystemRDL, assertion, 작업 지시서, 증거 묶음, gating 정책 |
| 답하는 질문 | 누가, 무엇을, 왜, 지금 어디까지 | 정확히 무엇이 통과인가, 실제로 통과했는가 |
| 바꾸는 방법 | 워크플로 전환과 댓글 | MR과 리뷰 |

둘을 잇는 규칙은 세 가지다.

1. **git → Jira.** Commit 메시지, branch 이름, MR 제목에 이슈 키를 쓴다. 연동이 켜져 있으면 이슈의 개발 패널에 나타난다. YAML 산출물에는 `jira:` 줄을 둔다(예: `jira: FEAT-341`).
2. **Jira → git.** 이슈에는 내용을 복사하지 않고 경로와 commit을 적는다. 수용 기준이나 통과 기준을 이슈 설명에 옮겨 적으면 원본이 둘이 된다.
3. **ID 읽는 법.** `REQ-207` 처럼 접두어와 숫자만 있으면 Jira 키다. `REQ-QOS-07`, `HSI-RCV-012`, `VER-REC-012` 처럼 가운데에 영역 약어가 있으면 git 산출물의 ID다. Jira 키는 `프로젝트 키-일련번호` 형식만 가능해서 `REQ-QOS-07` 은 키가 될 수 없다. 그래서 기존 ID는 그대로 두고 이슈의 필드에 싣는다.

이렇게 나누면 1편의 "실행 가능한 스펙이 원본"과 부딪히지 않는다. 1편의 문장 "추적은 표가 아니라 링크다"도 그대로다. 링크가 보이는 곳이 Jira가 될 뿐이다.

## 2. 이슈 유형 4가지

모두 사용자 정의 이슈 유형이다(표준 수준). 화면에서는 유형별 프로젝트 키를 쓴다. 팀이 과제별 단일 프로젝트를 쓰면 접두어만 과제 키로 바뀌고 나머지는 같다.

| 유형 | 키 | 필수 필드 | 워크플로 | 본편 사례의 예 |
|---|---|---|---|---|
| 요구사항 | `REQ-n` | 요구사항 ID, 출처 조항, 수용 기준 경로(git), 영향 블록(Component) | 제안 → 분석 중 → 승인 → 충족 확인. 반려 | `REQ-207` 수명 말기 read 지연 보장. ID `REQ-QOS-07`, `reqs/REQ-QOS-07.yaml` |
| 설계 기능 | `FEAT-n` | 블록(Component), 계약 ID와 경로, HW 담당, FW 담당 | 정의 중 → 구현 중 → 검토 대기 → 승인. 재확인 필요 | `FEAT-341` rcv_ctrl 복구 완료 전달. 계약 `HSI-RCV-012` |
| 검증 항목 | `VER-n` | 판정 장소(sim·formal·emulation·제품 테스트), 작업 지시서 경로, 증거 경로, 구성(RTL·TB·FW commit) | 정의 중 → 지시됨 → 진행 중 → 검토 대기 → 승인. 재확인 필요 | `VER-512` 완료 유실·중복 없음, `tasks/VER-REC-012.yaml`. `VER-530` 혼합 부하 P99.99 (emulation) |
| 버그 | `BUG-n` | signature, 발견 단계, 재현(테스트와 seed), 근거(파형·로그), 유출 단계(종결 때) | 초안 → 등록 → 수정 중 → 검토 대기 → 종결 | `BUG-2291` 완료 2건이 한 비트에 겹침 (emulation). `BUG-2304` full 직후 push 1건 유실 (sim) |

- 1편의 bug 기록 YAML의 칸(signature, found_at, repro, waveform, escaped_from)이 버그 이슈의 필드가 된다. 재현 테스트 자체는 git에 있다.
- "검토 대기"는 네 유형에 공통이다. 에이전트가 갈 수 있는 마지막 상태다.
- "재확인 필요"는 본편 8장의 표현 그대로다. 구성이 바뀌었거나 연결된 버그가 등록됐을 때 들어간다.

**작업 지시는 별도 유형으로 만들지 않는다.** 지시의 단위는 검증 항목(또는 설계 기능) 이슈다. 사람이 이슈를 에이전트 계정에 할당하고 "지시됨"으로 옮기는 것이 지시다. 3편의 작업 지시서 `tasks/VER-REC-012.yaml` 은 git에 그대로 있고, 이슈 설명에는 `intent` 한 줄과 지시서의 경로·commit만 적는다. `pass` 와 `forbid` 는 저장소 권한으로 지켜야 하므로 Jira로 옮기지 않는다. 지시를 쪼갤 때는 표준 유형인 하위 작업(Sub-task)을 쓴다.

계층(Epic → 표준 유형 → 하위 작업)은 추적에 쓰지 않는다. 부모는 하나만 둘 수 있는데 추적은 다대다이기 때문이다. Epic은 블록이나 마일스톤 묶음으로만 쓴다.

## 3. 링크 유형과 추적 사슬

사용자 정의 링크 유형 넷을 만든다. 표의 "나가는 방향"이 링크를 만드는 쪽이다.

| 링크 이름 | 나가는 방향 | 들어오는 방향 | 뜻 |
|---|---|---|---|
| Implements | FEAT `implements` REQ | REQ `is implemented by` FEAT | 이 기능이 이 요구사항을 구현한다 |
| Verifies | VER `verifies` FEAT 또는 REQ | `is verified by` | 블록 수준 기준은 FEAT에, 시스템 수준 수용 기준은 REQ에 직접 건다 |
| Fails | BUG `fails` VER | VER `is failed by` BUG | 이 버그 때문에 이 항목이 통과하지 못한다 |
| Affects | BUG `affects` REQ | REQ `is affected by` BUG | 요구사항에서 버그를 한 번에 찾는 지름길. 버그 초안을 쓸 때 함께 건다 |

과거의 비슷한 버그는 기본 유형 `relates to` 로 잇는다. MR과 commit은 링크가 아니라 개발 패널에 나타난다.

본편 사례의 사슬이다. 화면에 그대로 옮긴다.

```text
REQ-207  요구사항  REQ-QOS-07 · P99.99 read ≤ 2 ms
 ├─ is implemented by ─ FEAT-341  rcv_ctrl 복구 완료 전달
 │    │                  계약 HSI-RCV-012 · MR !2291
 │    └─ is verified by ─ VER-512  완료 유실·중복 없음
 │         │               a_no_drop · two_done_b2b
 │         └─ is failed by ─ BUG-2304  full 직후 push 유실
 ├─ is verified by ─ VER-530  혼합 부하 P99.99 (emulation)
 │    └─ is failed by ─ BUG-2291  완료 2건이 한 비트에 겹침
 └─ is affected by ─ BUG-2291, BUG-2304
```

읽는 순서는 본편과 같다. Emulation 항목 `VER-530` 이 `BUG-2291` 로 실패했고, 그 수정이 계약 v2와 MR !2291이며, 그 MR의 선택 실행에서 `VER-512` 가 `BUG-2304` 를 잡았다.

## 4. 사람과 AI가 Jira를 쓰는 방식

**(a) 현황 파악.** 사람은 보드와 저장한 필터, 대시보드를 본다. 에이전트는 같은 내용을 JQL로 읽는다.

```text
# 1. 검증 항목이 연결되지 않은 승인된 요구사항
project = REQ AND status = 승인
  AND issueLinkType != "is verified by"

# 2. REQ-207에 걸린 열린 버그
issue in linkedIssues("REQ-207", "is affected by")
  AND statusCategory != Done

# 3. 나에게 지시된 일 (에이전트 계정으로 실행)
assignee = currentUser() AND status in (지시됨, "진행 중")
  ORDER BY priority DESC
```

2번과 3번은 기본 JQL이다. 1번의 `issueLinkType` 은 Cloud 문서에서만 확인했고 부정 조건의 동작은 확인하지 못했다. DC에서는 검색 확장 앱이 필요할 수 있다(예: ScriptRunner의 `hasLinks`). 앱이 없어도 에이전트는 REST로 이슈의 링크 목록을 받아 스스로 걸러 낼 수 있다. 두 단계 이상 건너는 질의(요구사항 → 검증 항목 → 버그)는 기본 JQL로 안 되므로 `Affects` 지름길을 뒀다.

**(b) 업무 지시.**

1. 사람이 이슈를 에이전트 계정에 할당하고 "지시됨"으로 옮긴다. 작은 지시는 댓글에서 계정을 언급한다.
2. 에이전트가 "진행 중"으로 옮기고 일한다. 스펙이 모호하면 멈추고 댓글로 질문한다.
3. 끝나면 댓글 한 건에 결과 요약, 증거 경로와 commit, 확인하지 못한 것을 적고 "검토 대기"로 옮긴다.
4. 사람이 증거를 보고 "승인" 또는 "반려"(진행 중으로 되돌림)로 전환한다. 전환 이력이 승인 기록이다.

**(c) 신규 요구사항.** 누구나 요구사항 이슈를 "제안" 상태로 만든다. 자동화 규칙이 에이전트를 부르고, 에이전트가 영향 분석을 댓글로 단다(겹치는 요구사항, 영향받는 기능과 검증 항목, 확인하지 못한 것). 요구사항 담당이 승인하면 그때 요구사항 ID가 붙고 수용 기준 파일이 MR로 만들어진다. 필드에서 온 후보도 같은 길로 들어온다.

**(d) 에이전트의 권한.**

| 할 수 있다 | 할 수 없다 |
|---|---|
| 조회, 댓글 | 승인, 종결, 충족 확인, sign-off 전환 |
| 링크 추가 | 요구사항의 승인·반려 |
| "검토 대기"까지의 전환 | 수용 기준, 통과 기준, gating 정책 변경 (git에서 사람 소유) |
| 버그를 "초안"으로 생성 | 버그 초안의 "등록" 전환, waiver 등록 |
| 요구사항을 "제안"으로 생성 | 링크와 이슈 삭제 |

권한은 두 곳에서 건다. Jira에서는 승인 계열 전환에 "사람 역할만" 조건을 두고, 에이전트 역할에는 삭제 권한을 주지 않는다. git에서는 3편의 `forbid` 경로를 저장소 권한으로 막는다. 수용 기준이 git에 있으므로 에이전트가 이슈를 편집할 수 있어도 기준은 바꾸지 못한다.

에이전트가 쓴 것은 세 가지로 드러낸다. 역할별 전용 계정(`req-agent`, `dv-agent`, `triage-agent`. 사람 계정을 빌려 쓰지 않는다), 에이전트가 만든 이슈의 라벨 `ai-authored`, 댓글 첫 줄의 머리말 `[에이전트 · 계정 · 종류]`.

```text

```

## 6. 기존 6편과의 대응

| 영상 | 지금의 요소 → Jira의 무엇 | 새로 보여 줄 것 |
|---|---|---|
| 본편 | 요구사항 카드 → 요구사항 이슈 `REQ-207` (카드 머리의 `REQ-QOS-07` 은 유지). 단계마다 카드에 붙던 "기록" → 링크된 이슈. 퀄 패키지 → 링크를 따라 모은 증거 | 카드에 Jira 키와 상태 칩. 기록이 붙을 때 링크 이름. S5의 티켓은 버그 초안. 사람이 댓글로 지시하는 장면 한 번 |
| 1편 산출물 | 추적 그래프 한 줄 → 3장의 사슬. Bug 기록 카드 → 버그 이슈의 필드 | 계약 YAML에 `jira: FEAT-341` 한 줄. "원본은 git, 링크는 Jira" 문장. `BUG-2291` 의 `fails VER-530` |
| 2편 프로세스 | 영향 분석의 MR 댓글 → 이슈 키로 Jira에도 나타남. 가설 티켓 `RCV-1432` → `BUG-2304` 초안. `allow_known_issues` → 등록된 버그에 연결된 실패만 | MR 제목의 이슈 키. 티켓 머리의 "초안 · triage-agent". 16:10의 승인이 전환이라는 것 |
| 3편 업무 방식 | 작업 지시서 → `VER-512` 에 연결(원본은 git). 증거 묶음 요약 → 에이전트의 댓글과 경로. 반려·승인 → 워크플로 전환 | 할당으로 지시하는 장면. "검토 대기"에서 멈추는 에이전트. 승인 버튼은 사람 화면에만 |
| 4편 시스템 | 도구 `tracker` → Jira. `tracker.draft` → `jira.draft`. 유사 bug 검색 결과 → `BUG-1187` 과 `relates to` | 호출 기록 첫 줄에 `jira.search` (JQL). 권한 정책의 `jira: draft`. 초안 `BUG-2268` 이 `REQ-207` 에 연결되는 것 |
| 5편 문화 | "티켓 이력" → Jira의 변경 이력. 재분류 → 사람이 고친 링크와 필드 | `ai-authored` 로 거른 재분류율. 주간 공유의 저장한 필터. `F-007` 은 git에 그대로 두고 해당 버그에 댓글로 연결 |

**바꿀 이름.**

| 지금 | 바꿈 | 위치 | 이유 |
|---|---|---|---|
| `RCV-1432` | `BUG-2304` | 2편 | 버그 키 형식 통일 (필수) |
| `BUG-2291` (이전 과제의 유사 bug) | `BUG-1187` | 4편 | 1편의 `BUG-2291` 은 현 과제의 emulation bug다 (필수) |
| `tracker.draft`, `tracker: draft` | `jira.draft`, `jira: draft` | 4편 | 도구가 Jira임을 드러냄 (필수) |
| `C-RCV-02`, `C-RCV-03` | `HSI-RCV-012`, `HSI-RCV-013` | 2편 | 1편과 계약 ID 체계 통일 (권장) |
| `rec_ctrl` | `rcv_ctrl` | 3편 | Component 이름 하나 (권장) |

그대로 두는 것: `REQ-QOS-07`, `AC-1`, `HSI-RCV-012`, `VER-REC-012`, 1편의 `BUG-2291`, `MR !2291`, `F-007`, `tasks/`, `evidence/`, assertion과 테스트 이름. `BUG-2291` 과 `MR !2291` 은 번호가 같지만 체계가 다르다. 우연이고 의미를 두지 않는다.

## 7. 도입 순서와 지키는 선

1. **지금 쓰는 Jira에 유형과 링크를 더한다.** 이슈 유형 넷, 링크 유형 넷, 워크플로, 에이전트 계정과 역할. 블록 하나(`rcv_ctrl`)의 요구사항과 기능만 옮긴다.
2. **git과 잇는다.** 이슈 키 규칙, 개발 도구 연동, YAML의 `jira:` 줄. Commit 메시지로 이슈 상태를 바꾸는 기능은 끈다.
3. **에이전트는 읽기부터.** JQL 조회와 댓글만 허용한다. 영향 분석 댓글과 버그 초안으로 시작한다.
4. **지시와 전환을 연다.** 할당으로 지시하고 "검토 대기"까지 전환을 허용한다. 추적 공백을 주간 지표로 본다.

**지키는 선.**

- **Jira는 문서 창고가 아니다.** 기준과 증거를 붙여 넣지 않는다. 경로와 commit만 적는다.
- **링크는 검사된다.** 승인된 요구사항에 검증 항목이 없거나, 검증 항목에 증거 경로가 없으면 필터에 뜬다. 링크는 산출물의 `jira:` 줄과 주기적으로 대조한다.
- **댓글은 전환당 한 건.** 에이전트는 진행 상황을 댓글로 흘리지 않는다. 질문, 결과, 영향 분석만 쓴다. 상세 기록은 증거 묶음과 감사 기록에 있다.
- **승인은 사람 명의.** 승인 계열 전환과 waiver는 사람 역할에만 있다. 에이전트의 "검토 대기"는 완료 선언이 아니다.

## 8. 근거와 미확인

2026-11-11에 확인했다. 검색 요약에 기대는 항목은 [S]로 표시했다.

| 내용 | 출처 | 확인 |
|---|---|---|
| 이슈 키는 `프로젝트 키-번호`. 프로젝트 키는 대문자로 시작하고 대문자·숫자·밑줄만 가능 (DC 기준, 형식은 관리자가 조정) | Atlassian "Changing the project key format" | [S] Cloud 규칙은 미확인 |
| 기본 계층은 Epic → 표준 유형 → 하위 작업. Epic 위 단계 추가는 Cloud Premium·Enterprise | Atlassian Support, 커뮤니티 답변 | [S] |
| `linkedIssues(키, 링크 유형)` 은 기본 JQL. `issueLinkType` 은 Cloud 문서에 예가 있음 | Atlassian KB "Retrieve Linked Work Items by Link Type in Jira Cloud" | 원문 확인. 문서는 Cloud 전용 |
| 전환 조건으로 프로젝트 역할을 검사할 수 있다. 자동화 규칙에는 실행 계정(rule actor)이 있다. DC는 9.0부터 자동화가 기본 포함 | 커뮤니티 답변, DC release notes | [S] |
| Commit·branch·MR 제목의 이슈 키가 개발 패널에 연결된다. Cloud는 GitLab for Jira Cloud 앱, DC는 DVCS connector | GitLab 문서, Atlassian Support | [S] |
| Atlassian MCP server: `mcp.atlassian.com/v2/mcp`, OAuth 2.1(API token은 선택), 사용자의 기존 권한 안에서 동작 | Atlassian Support 시작 문서 | 원문 확인 |
| 공식 MCP 서버는 Cloud만 지원. DC는 REST와 personal access token, 또는 커뮤니티 MCP 서버 | 제3자 안내 글 | [S] 공식 문서에서는 확인 못 함 |

**확인하지 못한 것과 팀 확인이 필요한 것.**

- 팀의 Jira가 Cloud인지 DC인지, 과제별 프로젝트인지 유형별 프로젝트인지. 4편은 사내망 전제이므로 DC라면 에이전트 연결은 REST를 감싼 사내 연결 서버가 된다.
- 사용자 정의 이슈 유형과 링크 유형은 양쪽 모두 관리자가 만들 수 있는 것으로 알고 있으나 이번에 원문을 확인하지 못했다. Cloud의 team-managed 프로젝트는 제약이 다르다.
- `issueLinkType` 의 부정 조건, `linkedIssues` 의 방향 표기, 한글 상태 이름의 따옴표 처리는 팀 환경에서 한 번 실행해 봐야 한다.
- 전환 때 필수 필드를 검사하는 기능과 필드 단위 편집 제한은 배포 형태와 앱에 따라 다르다. 이 문서는 git 쪽 권한에 기대도록 설계했다.
- 요구사항 추적 앱(Xray, R4J, RTM 등)은 이름만 알고 있고 이번에 조사하지 않았다. 이 모델은 앱 없이 동작하도록 짰다.
- 에이전트 전용 계정의 라이선스 비용, 팀이 이미 쓰는 이슈 유형·워크플로와의 충돌.
