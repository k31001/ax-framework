# SSD 컨트롤러 SoC 개발 AX 전략 제안

> 상태: 승인 대기 초안 (2026-11-10)
> 근거: `docs/research/` 의 도메인별 리서치 4건. 이 문서의 수치는 모두 공개 자료에서 왔고, 팀의 목표 수치는 넣지 않았다.

## 1. 한 문장

**AI 도입을 넘어, AI 중심 재설계.**

AI를 지금의 일에 끼워 넣는 데서 멈추지 않고, AI를 전제로 일을 다시 설계한다. 재설계 대상은 다섯 가지다: 산출물, 프로세스, 업무 방식, 시스템, 문화.

## 2. 왜 지금의 방식으로는 부족한가

지금 팀의 AI 활용은 개인·작업 단위에 모여 있다. 코드 초안, 스크립트, 로그 요약, 문서 질의 같은 일이다. 이 일들은 가치가 있고 계속해야 한다. 다만 이것만으로는 과제 단위의 성과가 바뀌지 않는다. 이유는 세 가지다.

1. **작성은 일정의 일부다.** Siemens EDA는 칩 프로젝트 엔지니어링 노력의 60~70%가 검증 몫이라고 밝혔다(2025-09). SoC 일정을 지배하는 것은 RTL·코드 작성이 아니라 검증 수렴, HW/SW 통합, 퀄이다.
2. **병목은 사라지지 않고 옮겨간다.** 소프트웨어 조직의 텔레메트리에서, 개발자당 작업 처리량이 늘어난 조직은 첫 리뷰까지의 대기 시간과 개발자당 버그도 함께 늘었다(Faros AI, 2026-04, 자사 발표). 작성이 빨라지면 리뷰·검증·통합 대기열이 길어진다.
3. **일의 형태가 그대로면 에이전트를 들여도 작업 보조에 머문다.** EDA 3사가 2026년에 내놓은 워크플로 에이전트는 모두 스펙과 설계 의도를 입력으로 전제한다. 스펙이 PDF·엑셀·메일에 흩어져 있고 에이전트가 시뮬레이터나 보드를 스스로 돌릴 수 없으면, 좋은 모델을 써도 사람이 사이사이를 이어야 한다.

그래서 필요한 것이 process innovation이다. 손 닿는 열매를 따서 아낀 시간은 버리는 것이 아니라 다음 단계의 재원으로 쓴다.

**이 논지의 단서.** 공개된 반도체 사례는 대부분 워크플로 에이전트 도입 초기 단계이고, 수치는 거의 전부 자사 발표다. 프로세스 전체를 AI 중심으로 재설계해 tape-out 성과가 좋아졌다는 독립 실증은 찾지 못했다. 그래서 이 전략은 한 번에 뒤집는 계획이 아니라, 단계마다 측정하고 확인하면서 나아가는 계획이다.

## 3. 성숙도 3단계

| | L1 작업 보조 | L2 워크플로 에이전트 | L3 프로세스 재설계 |
|---|---|---|---|
| 적용 단위 | 개인의 작업 | 워크플로 | 과제 전체의 흐름 |
| AI가 하는 일 | 초안, 요약, 질의응답 | 툴을 직접 돌리고 결과를 보고 반복 | 프로세스가 에이전트를 전제로 짜여 있음 |
| 사람이 하는 일 | 작성 | checkpoint 승인 | 의도 정의, 검증 기준 설계, sign-off |
| 산출물 | 기존 문서 그대로 | 일부가 기계가 읽는 형식 | 실행 가능한 스펙이 단일 원본 |
| 다음 단계로 가는 조건 | 사용 현황과 기준선 확보 | 워크플로별 평가와 추적성 확보 | (지속 운영) |

지금 팀은 L1에 있다. EDA 벤더가 쓰는 "Level 1~5"는 툴이 얼마나 혼자 일하는지를 재는 척도라서 이 표와는 다른 축이다.

## 4. 3대 원칙과 불변 원칙 하나

전 과정에 공통으로 적용한다. 네 건의 리서치가 서로 다른 영역에서 같은 결론에 닿았다. 앞의 셋은 바꾸는 방향이고, 넷째는 바꾸지 않는 것이다.

1. **스펙 원본화.** 사람이 읽는 문서를 기계가 읽고 실행하는 스펙으로 바꾼다. RTL, testbench, assertion, FW driver, 테스트는 스펙에서 파생되고 다시 생성할 수 있는 결과물이 된다. 업계도 새로운 병목을 "스펙의 명확성"으로 지목한다(SemiEngineering, 2026-06).
2. **폐루프 자동화.** 에이전트가 시뮬레이터, formal, emulator, 빌드, 보드, 로그에 직접 닿아 실행하고 결과를 보고 고칠 수 있게 한다. NVIDIA 자체 평가에서 같은 모델의 RTL 디버깅 통과율은 단독 44.0%에서 에이전트 루프 94.3%로 올랐다(2026-07). 차이는 모델이 아니라 루프에서 나왔다.
3. **전 과정 추적성.** 요구사항, 설계, 검증, FW, 테스트, 퀄 증빙을 하나의 추적 가능한 그래프로 연결한다. 변경은 이벤트가 되어 영향 범위가 계산되고, 필드에서 배운 것은 다음 과제의 요구사항으로 돌아온다.
4. **작업은 자동화, 책임은 사람.** Gate와 sign-off는 없애지 않는다. Arm 소속 엔지니어의 실험에서 세 모델은 스스로 정한 검증 목표를 100% 달성하고 sign-off를 선언했지만, 심어 둔 bug 806개 중 최고 모델도 20.8%를 놓쳤다(SemiEngineering, 2026-11). 에이전트의 완료 선언은 증거가 아니다. 자율 수준은 작업을 되돌릴 수 있는지로 정한다. Triage나 초안은 자율에 맡기고, tape-out과 고객 출하 FW는 gate로 둔다.

## 5. 5대 전환

| 축 | 지금 | 지향점 | 첫걸음 |
|---|---|---|---|
| 산출물 | 사람이 읽는 Word·PDF 스펙, 엑셀 추적표, 자유 서술 bug report | 기계가 읽고 실행하는 스펙, 요구사항–설계–테스트 추적 그래프, 구조화된 증빙 | Register 정의를 넘어 동작 규약(interrupt 규칙, 초기화 순서)까지 담는 HW/SW interface 스펙부터 |
| 프로세스 | 순차 handoff, 야간 regression 뒤 수동 분류, 말미에 몰리는 통합과 퀄 | Gate는 유지하고 gate 사이를 상시 루프가 메우는 연속 흐름 | 작성 단계가 아니라 대기열이 쌓이는 곳(regression triage, 영향 분석)부터 |
| 업무 방식 | 직접 작성하고 동료가 전수 리뷰 | 의도를 정의하고, 에이전트를 운용하고, 증거로 판단 | 생성하는 경로와 검증하는 경로를 분리하는 규칙 |
| 시스템 | 각자 쓰는 챗봇, 툴과 연결되지 않음 | 사내 모델, 툴 연동, 설계 지식 그래프, 평가 체계, 권한·감사를 갖춘 AI 플랫폼 | 에이전트가 시뮬레이터와 로그에 닿는 통로 하나 |
| 문화 | 개인의 요령, 측정하지 않는 사용 | 측정하고 공유하고 학습하는 팀, 역할 변화에 맞춘 평가와 육성 | 기준선 측정과 사례 공유의 정례화 |

역할 변화는 이렇게 요약된다. 엔지니어의 자리는 없어지지 않고 무게중심이 옮겨간다. 작성하는 사람에서, 무엇을 만들지 정하고 무엇으로 통과를 판정할지 설계하고 그 결과에 서명하는 사람으로.

## 6. 전 과정 7단계

| # | 단계 | 지금의 병목 | L2: 워크플로 에이전트 | L3: 재설계 후 |
|---|---|---|---|---|
| 1 | 요구사항 취합·분석 | 고객 요구, 표준(NVMe·PCIe·NAND interface·TCG), 로드맵이 따로 바뀌고, 추적은 엑셀 수작업 | 표준 개정판과 요구서를 조항 단위로 추출해 충돌·누락 후보를 보고 | 요구사항이 그래프로 존재. 한 줄을 고치면 영향받는 블록·레지스터·테스트가 계산됨 |
| 2 | 아키텍처 설계 | 모델링 비용이 커서 후보가 소수. HW/FW 경계는 초기에 정하고 재평가하지 않음 | 에이전트가 시뮬레이터를 돌려 설계 공간을 탐색하고 Pareto 리포트 작성 | 아키텍처가 실행 가능한 모델과 결정 기록으로 남고, 사람은 목적과 제약을 정해 후보 중에서 고름 |
| 3 | IP 설계·조합, PPA 최적화 | 스펙·RTL·register map·FW 헤더가 따로 유지되어 어긋남. 통합 이슈와 PPA 문제가 뒤늦게 드러남 | 생성 → lint·sim·formal → 수정 반복, PPA 파라미터 자동 탐색 | 스펙에서 RTL·헤더·assertion이 함께 파생. PPA가 RTL commit마다 돌아오는 피드백이 됨 |
| 4 | IP·SoC 시뮬레이션 검증 | 스펙 → testplan → TB → assertion의 직렬 번역, coverage 수렴의 마지막 구간, regression 실패의 수동 분류 | 에이전트가 TB 생성·실행·coverage 분석을 반복하고, 실패를 묶어 원인 가설과 재현 seed를 붙임 | commit마다 영향 분석 → 선택 실행 → 분류로 이어지는 상시 검증. 사람은 독립 기준과 sign-off를 소유 |
| 5 | Emulator·FPGA, HW/SW co-verification | 고가 장비 대기열, 긴 워크로드 끝의 실패 재현, 실리콘에 가까워서야 만나는 HW와 FW | 실패 signature로 trigger 설정 → 재실행 → 작은 재현 케이스로 축소 | 상시 가동 워크로드 팜. RTL과 FW가 같은 파이프라인에서 매일 만나 실제 FW로 부팅 |
| 6 | SoC 구동 SW/FW 개발 | HW 스펙을 손으로 옮기고, 변경이 늦게 전파되고, 빌드·flash·로그 확인이 사람 손에 묶임 | 에이전트가 빌드 → 가상 플랫폼·보드 실행 → 로그 수집 → 수정 반복 | 실행 가능한 HW/SW interface 스펙에서 driver 골격과 테스트가 파생. 스펙 변경이 곧 FW 변경 제안 |
| 7 | 제품 테스트, 퀄 승인 | 테스트 조합 폭발, 불량 로그 분석의 전문가 의존, 말미의 증빙 취합, 느린 필드 환류 | 실패 자동 분류와 중복 제거, 증빙을 모아 리포트 조립(수치마다 원본 연결) | 사람은 신규 불량 판단과 처분에 집중. 추적 기록은 개발 내내 누적되고 퀄 판정은 사람이 함. 필드 이슈는 다음 요구사항 후보로 돌아옴 |

7단계의 끝은 1단계로 이어진다. 이 고리가 닫히는 것이 재설계의 완성이다.

요구사항 하나가 이 7단계를 지나가는 구체적인 흐름은 `03-workflow-case.md` 에 사례로 풀어 썼다. 단계마다 에이전트가 하는 일과 사람이 하는 일, 문제가 나왔을 때의 해결 과정, 역할별 변화가 들어 있다.

**단계별 성숙도 차이.** 공개 제품과 사례가 가장 많은 곳은 4단계(시뮬레이션·formal·regression triage)와 3단계의 PPA 탐색이다. 1·2단계와 5단계는 상용 에이전트가 얕아서 팀이 직접 설계해야 하는 영역이다. 7단계에서 통계적 표본과 시험 시간 자체는 AI로 줄지 않는다. 줄일 수 있는 것은 대기, 취합, 재작업이다.

## 7. 로드맵

| 단계 | 핵심 | 다음으로 넘어가는 조건 |
|---|---|---|
| ① 기반 구축 | 사내 모델과 툴 연동, 데이터 등급 정책, 주요 워크플로의 기준선 측정, 지금의 작업 보조 활용 정리와 공유 | 주요 워크플로의 기준선과 평가 세트가 있음 |
| ② 병목 우선 에이전트화 | 대기열이 쌓이는 워크플로부터 닫힌 루프로 전환(regression triage, 영향 분석, 테스트 생성, 로그 분석). Checkpoint와 감사 기록. 산출물을 기계가 읽는 형식으로 | 워크플로 단위의 품질과 비용을 상시 측정 |
| ③ 프로세스 재설계 | 실행 가능한 스펙 중심의 흐름, 상시 검증, 역할과 평가 체계 개편 | 과제 단위 지표의 개선 추세, gate 증빙의 자동 생성 |

기간은 정하지 않았다. 기준선을 측정한 뒤 단계별 조건으로 판단한다. 참고로 업계의 공개 일정은 아래와 같다.

| 주체 | 공개된 일정 | 시사점 |
|---|---|---|
| Synopsys | AgentEngineer를 2025-03에 공개. 2026-09에 Autopilot Platform과 에이전트 7종 발표, 정식 출시는 2026년 말 예정 | ② 단계의 도구가 상용화 구간에 들어섬 |
| Cadence | ChipStack AI Super Agent를 2026-02에 발표. Early access는 2026년 하반기 | 같음 |
| Siemens | Questa One Agentic Toolkit(2026-02, early access), Fuse EDA AI Agent(2026-03) | 같음 |
| SK hynix | 사내 로드맵: 2023 RAG와 LLM → 2024 에이전트와 업무 도구 → 2025 에이전트 오케스트레이션 | 기반에서 에이전트 오케스트레이션까지 약 2년 (제조를 포함한 전사 기준) |
| Samsung DS | 사내 coding agent를 2023년부터 운영, 개발자 1만 명 이상 사용. 2026-03에 multi-agent 설계 workflow 발표 | 사내 도구 운영에서 multi-agent workflow 발표까지 약 3년 |

일정은 모두 각 회사의 발표다. ③ 단계까지 갔다고 공개한 곳은 찾지 못했다.

순서를 정하는 원칙은 네 가지다.

- 병목 먼저. 작성이 아니라 대기열이 쌓이는 곳부터 한다.
- 되돌릴 수 있는 일 먼저.
- 측정이 자율보다 먼저.
- ①에서 아낀 시간은 ②를 만드는 데 다시 쓴다.

## 8. 지표 후보

목표 수치는 기준선을 측정한 뒤에 정한다. 속도 지표는 항상 품질 guardrail과 쌍으로 본다.

- **흐름**: 스펙 변경에서 검증 완료까지의 시간, regression triage 시간, 검증 수렴 기간, 리뷰 대기 시간
- **결과**: pre-silicon bug escape, re-spin 횟수와 원인, 퀄·고객으로 넘어간 FW 결함, 퀄 1회차 통과율
- **에이전트 품질**: 첫 시도 통과율, 심어 둔 bug의 검출률, 사람의 재작업률
- **비용**: 단위 작업당 token·compute·license, 리뷰에 쓴 엔지니어 시간
- **사람**: 시간 배분(작성·검토·debug·대기), 역량 평가
- **Guardrail**: 리뷰 없이 반영된 변경 비율, waiver 증가율

| 리스크 | 통제 방향 |
|---|---|
| 설계 IP와 고객 자료 유출 | 사내·격리 배포, 데이터 등급별 모델 경로, 접근 권한과 감사 기록 |
| AI 산출물의 오류와 자기 채점 | 판정은 시뮬레이터·formal 같은 결정론적 툴이 하고, 심어 둔 bug와 에이전트가 본 적 없는 평가 세트로 측정 |
| 설계와 검증이 같은 오해를 공유 | 생성 경로와 검증 경로 분리, 사람이 소유한 reference model |
| Sign-off 책임의 모호함 | Sign-off는 사람 명의. 에이전트의 완료 선언은 증거로 인정하지 않음 |
| 속도 지표 착시 | 처리량과 품질 지표를 쌍으로 보고 |
| 비용 증가 | 탐색 compute와 token 비용을 처음부터 지표로 관리 |
| 과의존과 역량 공동화 | 주니어의 직접 debug 구간 유지, 역량 지표 추적 |

**한계.**

- 6장의 "지금의 병목"은 업계 일반론이다. 팀의 실제 상황과 대조해서 고쳐야 한다.
- L3의 모습은 공개 근거에서 끌어낸 제안이다. 완성된 공개 사례는 없다.
- SSD 컨트롤러 전문 업체가 설계·검증·FW 프로세스에 AI를 적용한 공개 사례는 드물다. 가장 가까운 것은 Kioxia의 구현 단계 사례와 Solidigm의 사내 도구 소개다.
- 벤더가 발표한 생산성 수치(10배, 40배, 50배 등)는 대상 설계와 기준선이 공개되지 않아 이 문서에서 근거로 쓰지 않았다.
