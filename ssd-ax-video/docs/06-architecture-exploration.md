# 구조 설계 편: RTL 먼저 → 모델로 먼저 검증

> 상태: 초안 (2026-11-12). 본편 `03-workflow-case.md` 3~4장을 RTL 설계자 관점에서 확대한 문서다. 대본은 `src/shifts/arch/script.json`.

> Jira의 이슈 키와 계정은 `05-jira-traceability.md` 의 모델을 따른다. `FEAT-330` 처럼 접두어와 숫자만 있으면 Jira 키, `ADR-RCV-003` 처럼 영역 약어가 있으면 git 산출물의 ID다.

## 1. 한 줄 요약

구조가 그대로일 때는 RTL을 먼저 짜는 것이 빠르다. HW/FW 경계가 움직이고 판정 지표가 P99.99 같은 시스템 통계일 때는, 구조 후보를 **보정된 모델**로 먼저 비교하고 RTL은 그 결과(블록별 예산, interface 계약)를 받아 시작하는 것이 빠르다. 지금까지 모델 먼저가 느렸던 이유는 모델을 만들고 보정하는 고정비였고, AX가 낮추려는 것이 바로 그 고정비다.

## 2. 논쟁: "RTL 먼저"와 "모델 먼저"

"빨리 RTL을 짜서 검증하고 고치는 것이 빠르다"는 판단은 틀린 것이 아니다. 조건이 붙은 판단이다.

| | RTL 먼저가 맞는 조건 | 모델 먼저가 맞는 조건 |
|---|---|---|
| 구조 | 이전 실리콘에서 검증된 구조를 유지 | HW/FW 경계나 블록 사이의 흐름이 바뀜 |
| 변경 범위 | 블록 안 (파라미터, FSM 상태, table) | Interface 계약이 여러 블록에서 바뀜 |
| 문제의 성격 | 국소적. 블록 검증에서 드러남 | 블록이 만나는 곳의 경쟁, 큐, 분담 |
| 판정 지표 | 블록 수준의 기능과 cycle 수 | 시스템 통계 (지연 꼬리, 평균 전력) |
| 틀렸을 때 | 그 블록의 RTL을 고침 | 여러 블록, HSI, FW, 검증 환경을 고침 |

**지금까지 RTL 먼저가 합리적이었던 이유.**

1. 과제 대부분이 파생이었다. 구조는 이전 세대 실리콘이 이미 검증해 줬다.
2. 모델의 고정비가 컸다. 성능 모델을 새 NAND와 새 구조에 맞게 고치고 실측에 맞추는 일은 소수의 아키텍트 손에 있었다. 그 사이에 RTL은 이미 나왔다.
3. 보정되지 않은 모델은 믿기 어렵다. 공개 SSD 시뮬레이터 MQSim도 실제 SSD 네 종과의 오차를 6~18%로 보고한다(저자 수치). 믿지 못할 모델보다 RTL이 낫다는 판단은 타당했다.
4. RTL은 timing과 면적이라는 실제 수치를 준다.

**구조가 크게 바뀌면 달라지는 것.**

- **늦게 드러난다.** P99.99를 판정하려면 꼬리 표본이 수천 건, 곧 read가 수천만 건 필요하다. RTL 시뮬레이션으로는 돌릴 수 없는 양이다. 이 지표를 RTL로 처음 보는 것은 RTL과 FW가 emulator·FPGA에 함께 오른 뒤다.
- **비싸게 드러난다.** 그 시점에는 RTL, HSI(register, C++ header), FW 복구 경로, 검증 환경이 그 구조 위에 서 있다.
- **한 번에 한 구조만 시험한다.** RTL로 후보 넷을 비교할 수는 없다.

숫자로 보면 이렇다. NAND read 한 건은 100 µs 안팎이고, 1 GHz clock이면 10만 cycle이다. SoC 수준 RTL 시뮬레이션이 초당 수백~수천 cycle을 돈다고 하면 read 한 건에 분 단위가 든다. Read 5천만 건은 시뮬레이션의 영역이 아니다. Emulator는 이 양을 돌릴 수 있지만 RTL과 FW가 모두 있어야 한다. "빨리 짜서 검증한다"의 검증에는 P99.99가 들어 있지 않다.

Synopsys의 Tim Kogel은 구조 결함이 RTL과 SW가 처음 함께 도는 system validation에서야 드러난다고 썼다(2021, 벤더 블로그, 수치 없음). 늦은 발견의 비용 배수를 독립적으로 잰 자료는 찾지 못했다.

**AX가 바꾸는 계산.**

```text
모델 먼저의 비용 = 모델 구축·보정 (고정비) + 탐색 시간
모델 먼저의 이득 = 구조 문제가 있을 확률
                   × 늦게 발견했을 때 되돌아가는 범위
```

에이전트가 줄이는 것은 고정비다. 이전 세대 모델에서 후보별 변형을 만들고, 실측 로그에 맞춰 보정하고, 수백 구성을 돌리고, 결과를 표로 정리한다. 고정비가 내려가면 손익분기점이 더 작은 변경 쪽으로 옮겨 간다.

| 모델 먼저의 일 | 지금 | 에이전트가 맡을 수 있는 부분 | 사람에게 남는 부분 |
|---|---|---|---|
| 후보별 모델 만들기 | 아키텍트가 기존 모델을 손으로 고침 | 기존 모델에서 후보별 변형을 생성하고 단위 테스트로 확인 | 모델 구조의 검토, 빠진 경쟁 경로 지적 |
| 보정 | 실측 로그를 손으로 정리해 파라미터를 맞춤 | 로그에서 분포를 뽑고 파라미터를 맞추고 오차표를 냄 | 실측 데이터 확보, 믿는 범위의 판단 |
| 탐색 | 두세 안을 몇 조건에서 | 수백 구성을 여러 시나리오에서 | 제약과 시나리오의 정의 |
| 약점 찾기 | 경험에 기댄 검토 | 나쁜 조건을 만들어 돌리고 원인을 좁힘 | 수정안의 선택 |
| 기록 | 회의록과 발표 자료 | 결정 기록 초안, 예산표 초안 | 결정과 승인 |

**근거가 약한 곳.** 고정비가 얼마나 줄어드는지 SSD 컨트롤러에서 잰 공개 수치는 없다. 에이전트 탐색의 공개 사례는 CPU와 가속기 대상이다. 그리고 에이전트가 줄이지 못하는 것이 있다. 보정에 쓸 실측 데이터를 모으는 일, 모델을 믿을 범위를 판단하는 일이다.

**변경 규모에 따른 판단 기준.**

| 규모 | 예 | 순서 |
|---|---|---|
| 소 | Retry table 확장, 큐 깊이 조정, FSM 상태 추가 | RTL 먼저 |
| 중 | Interface 한 곳 변경, 경계는 유지 | 기존 모델로 영향만 확인하고 RTL |
| 대 | HW/FW 경계 이동, 새 공유 자원, 새 NAND 세대와 지연 기준 변경 | 모델 먼저. 기간을 정해 놓고 한다 |

"대"로 보는 신호는 다섯이다. 하나라도 해당하면 모델 먼저다. ① HW/FW 경계가 움직인다 ② 새 공유 자원이나 경쟁 경로가 생긴다 ③ 판정 지표가 시스템 통계다 ④ Interface 계약이 두 블록 이상에서 바뀐다 ⑤ 틀리면 블록 하나 밖까지 되돌아간다.

이 판단은 과제 초기에 아키텍트와 RTL 리드가 함께 하고, 결과를 구조 결정 이슈에 한 줄로 남긴다. "모델 먼저"로 정했으면 기간을 먼저 정한다. 기간 안에 제약을 통과한 후보가 나오지 않으면 그 사실이 결과다. 요구사항을 다시 협의해야 한다는 뜻이기 때문이다.

둘은 배타적이지 않다. 모델 먼저여도 구조와 무관한 블록(host interface 세대 변경, 재사용 IP 이식)의 RTL은 병행한다. 후보에 공통인 블록은 RTL을 먼저 짜 보고 그 면적·timing 수치를 모델에 넣는다.

## 3. 구조 설계가 진행되는 순서

| # | 단계 | 누가 | 만드는 것 | 무엇으로 판단하나 |
|---|---|---|---|---|
| 1 | 목표와 제약 | 아키텍트 | 제약(넘으면 탈락)과 목적(작을수록 좋음)의 구분, 평가 시나리오 | 요구사항의 수용 기준 |
| 2 | 후보 세우기 | 아키텍트, RTL 설계자, FW 담당. 에이전트는 과거 결정 기록과 실측을 찾아 줌 | 후보 3~5개의 블록도와 HW/FW 분담 | 서로 다른 축을 건드리는가 |
| 3 | 구현 추정 | RTL 설계자 | 후보별 면적·timing 추정, 재사용할 IP와 새로 짤 블록 | 이전 과제의 합성 결과 |
| 4 | 모델 구축과 보정 | 에이전트가 만들고, 아키텍트가 검증 | 후보별 모델, 보정 리포트, 믿는 범위 | 이전 세대 실측을 재현하는가 |
| 5 | 탐색과 평가 | 에이전트 | 구성별 결과, 제약 통과 후보, 근거 | 제약 통과 여부 |
| 6 | 약점 찾기 | 에이전트, 검증 리드, FW 담당 | 나쁜 조건의 시나리오, 발견된 문제와 수정안 | 수정 후 재실행 |
| 7 | 선택과 기록 | 아키텍트가 결정. RTL 리드와 FW 리드가 함께 승인 | 결정 기록(ADR) | 사람의 판단 |
| 8 | 인계 | 아키텍트, RTL 설계자 | 블록별 예산, interface 계약, microarchitecture 출발점 | 예산의 합이 판정선 안인가 |

몇 단계를 풀어 쓴다.

- **2단계, 후보는 서로 다른 축을 건드려야 한다.** 같은 구조에서 숫자만 다른 것은 후보가 아니라 파라미터다. 후보는 "제어를 누가 하는가", "자원을 나누는가 따로 두는가"처럼 블록도가 달라지는 선택이다. 파라미터(decoder 수, 큐 깊이)는 5단계에서 에이전트가 후보 안에서 돌린다. "가장 적게 바꾸는 안"은 반드시 후보에 넣는다. 그 안이 통과하면 그것이 답이다.
- **3단계, RTL 설계자의 추정이 모델의 입력이다.** 면적과 전력은 성능 모델이 내지 못한다. RTL 설계자가 이전 과제의 합성 결과에서 비례 계산하거나, 후보 공통 블록을 짧게 짜서 합성해 본다. 추정에는 근거와 폭(±)을 붙인다.
- **4단계, 모델은 에이전트가 만들고 사람이 믿을지 정한다.** 아키텍트는 코드를 전부 읽는 대신 보정 리포트와 "이 모델이 표현하지 않는 것"의 목록을 본다.
- **6단계, 통과한 후보를 일부러 괴롭힌다.** GC가 몰릴 때, 특정 die에 요청이 쏠릴 때, FW가 바쁠 때 같은 조건을 더 돌린다. 검증 리드와 FW 담당이 위험한 때를 말하고 에이전트가 시나리오로 옮긴다.

Jira와 git에는 이렇게 나뉜다. 구조 결정은 설계 기능 이슈 한 건(`FEAT-330`)이고 `REQ-207` 에 `Implements` 로 이어진다. 후보, 모델, 결정 기록, 예산표의 원본은 git에 있고 이슈에는 경로와 commit만 적는다. 탐색 지시와 결과 보고는 이슈의 댓글이다. 구조 모델의 수용 기준 시나리오는 Xray Test(`VER-505`, 환경 `model`)이고, 실행 결과는 파이프라인이 Test Execution(`VER-506`)으로 올린다. 구조 확정은 `FEAT-330` 을 "정의 중"에서 "구현 중"으로 옮기는 전환이고 사람만 할 수 있다.

## 4. 관점과 모델

**관점.** "다양한 관점에서 시도한다"는 후보마다 아래 질문에 답을 채우는 일이다.

| 관점 | 질문 | 무엇으로 보나 | 지표 |
|---|---|---|---|
| 성능·지연 꼬리 | 수명 말기 혼합 부하에서 기준 안인가 | Trace 기반 성능 모델 | P99.99, 큐 대기 |
| 전력 | 전력 한도 안인가 | 활동률 × 블록별 전력 추정 | 평균·최대 전력 |
| 면적 | 면적 한도 안인가 | RTL 설계자의 추정, 이전 합성 결과 | 블록 면적 증가 |
| HW/FW 분담 | FW에 무엇이 남고 얼마나 복잡한가 | 가상 플랫폼, FW 담당의 검토 | FW 경로 수, FW 왕복 횟수 |
| 검증 가능성 | 이 구조는 무엇으로 검증하나 | 검증 리드의 검토 | Formal로 닫히는 속성, emulation에 남는 것 |
| 일정·재사용 | 기존 IP를 얼마나 살리나 | RTL 설계자의 판단 | 재사용 비율, 신규 블록 수 |
| 리스크 | 어떤 전제가 깨지면 무너지나 | 전제 목록과 민감도 실행 | 전제별 여유 |

전력은 성능 모델이 낸 블록별 활동률(decoder가 도는 시간의 비율, 큐 점유)에 RTL 설계자가 준 블록별 전력 추정을 곱해서 본다. 검증 가능성은 숫자가 아니라 표로 본다. 후보의 속성마다 "formal로 닫는다, 시뮬레이션으로 본다, emulation까지 가야 한다"를 적는다. Emulation까지 가야 판정되는 속성이 많은 후보는 문제가 늦게 드러나는 후보다.

**관점이 부딪힐 때.** 점수에 가중치를 곱해 더하지 않는다. 가중합은 지연 기준을 넘는 안이 면적 점수로 이기는 결과를 만든다. 먼저 **제약과 목적을 나눈다.** 지연, 전력, 면적 한도는 제약이고 넘으면 탈락이다. 남은 후보를 목적(면적, 리스크, FW 복잡도)의 Pareto로 놓고 사람이 고른다. 제약의 판정선에는 모델 오차만큼 여유를 둔다.

**모델의 종류와 충실도.**

| 모델 | 답하는 질문 | 답하지 못하는 질문 |
|---|---|---|
| 해석 모델 (수식, 스프레드시트) | 평균 지연, 필요한 자원 수의 규모, 어느 경로가 꼬리를 정하는가 | 경쟁과 burst, 꼬리의 값 |
| Trace 기반 성능 모델 (이산 사건) | 지연 분포와 꼬리, 큐 대기, GC와의 경쟁 | Cycle 수준 timing, 실제 FW 코드의 동작 |
| SystemC/TLM 가상 플랫폼 | 실제 FW가 도는가, HSI의 사용 순서, FW 실행 시간 | 긴 통계 (느리다), RTL timing |
| 실행 가능한 스펙 (블록 동작 모델) | 블록의 요청·완료 순서와 규칙 | 면적, 전력 |
| Formal 모델 (추상 상태 기계) | Deadlock, 굶는 요청이 없는가 | 성능 수치 |

충실도는 한 번에 올리지 않는다. 해석 모델로 어느 경로가 문제인지 먼저 좁히고, trace 기반 모델로 후보를 가르고, 고른 구조만 가상 플랫폼과 블록 동작 모델로 내려간다.

**보정.** 모델을 "이전 세대 구조, 이전 세대 NAND"로 설정하고 이전 실리콘의 실측 분포를 재현하는지 본다. 입력은 이전 제품의 단계별 지연 로그, FW 왕복 시간 분포, NAND 평가 데이터다. 실측 일부는 보정에 쓰지 않고 남겨 두었다가 확인에 쓴다.

순서는 넷이다. ① 실측에서 입력 분포를 뽑는다(단계별 NAND 시간, decode 시간, FW 왕복). ② 이전 세대 설정으로 돌려 출력 분포(P50, P99, P99.99)를 실측과 비교한다. ③ 차이가 큰 구간의 원인을 찾아 모델을 고친다. 파라미터를 결과에 맞춰 비트는 것이 아니라 빠진 동작을 넣는다. ④ 남겨 둔 실측(다른 부하, 다른 QD)으로 다시 확인한다. 새 NAND의 값은 실측이 없으므로 초기 평가 데이터를 쓰고, 그 값이 바뀔 때의 민감도를 함께 돌린다.

**믿는 범위.** 보정 리포트에 셋을 적는다. 오차(지표별), 덮는 조건, 덮지 않는 조건. 판정선은 오차만큼 낮춘다. 공개 사례에서도 모델은 실측에 맞춘 뒤에 쓴다. SSDExplorer는 실제 SSD와 비교해 검증했고, AmpereOne CPU 팀은 trace 기반 성능 모델과 RTL을 unit 단위부터 맞춰 간다(10장).

### 4.1 모델은 하나인가 여럿인가

성능, 전력, 면적, 기능을 모두 답하는 **통합 모델** 하나를 만들 것인가, 관점마다 추상화 수준과 기술 스택이 다른 **목적별 모델**을 둘 것인가.

| 기준 | 통합 모델 | 목적별 모델 |
|---|---|---|
| 구축·유지 비용 | 처음이 크다. 변경 하나가 전체에 걸린다 | 모델마다 작다. 개수가 늘어 유지할 대상이 많다 |
| 실행 속도, 후보 수 | 가장 느린 관점(실제 FW 실행, bit 단위 기능)에 묶인다. 후보를 몇 개만 돌린다 | 성능 모델은 기능을 확률과 시간 분포로 줄여 수백 구성을 돌린다 |
| 충실도 | 모든 관점에서 가장 높은 요구를 맞춰야 한다 | 관점마다 필요한 만큼만 |
| 보정 | 어긋났을 때 어느 부분이 틀렸는지 가르기 어렵다 | 모델마다 대조할 실측이 분명하다 |
| 관점 간 일관성 | 구조가 하나라서 저절로 맞는다 | **약점.** 모델마다 다른 구조를 가정할 수 있다 |
| 사람의 이해와 검증 | 크고 얽혀 있어 믿을 범위를 판단하기 어렵다 | 한 사람이 읽고 검증할 크기 |
| 에이전트의 생성·수정 | 수정의 영향 범위가 넓어 확인이 어렵다 | 작고 통과 기준이 분명해 만들고 고치기 쉽다 |
| RTL과의 정합 | 대조할 지점이 흐리다 | 예산은 성능 모델, 속성은 formal, 순서는 기능 모델이 맡는다 |

공개 자료는 목적별 쪽을 지지한다. 다만 SSD 컨트롤러에서 두 구성을 직접 비교한 자료는 없다.

- SystemC TLM-2.0 표준부터 용도별 작성 방식을 둘로 나눈다. Loosely-timed는 SW 개발용으로 가장 빠르게, approximately-timed는 구조 탐색에 쓸 만큼만 정확하게 쓴다.
- 성능 시뮬레이터에 전력·면적 모델을 붙여 한 번에 보는 방식(gem5와 McPAT)은 널리 쓰이지만, McPAT의 오차를 분석한 논문은 모델이 불완전하거나 실제 구현과 다른 구조를 가정해 오차가 크다고 보고했다(CPU 대상).
- 한 도구로 성능·전력·면적을 RTL 가까이 맞춘 사례(Aladdin, 저자 수치 0.9%, 4.9%, 6.6%)는 datapath 중심의 가속기로 범위를 좁힌 경우다.
- 구조 기술 하나를 여러 추정기가 함께 읽는 방식은 DNN 가속기의 Timeloop과 Accelergy에 있다. 같은 architecture 기술을 성능 모델과 에너지·면적 추정기가 읽고, 추정은 부품별 plug-in이 맡는다.
- 전력을 따로 시뮬레이션하지 않고 성능 모델의 활동에 상태별 전력을 얹는 방식은 표준(IEEE 1801-2015의 system-level power model)에 있다. 채택은 느렸고 초기 값은 추정이라는 지적이 있다.

**권고: 모델은 여럿, 구조 기술은 하나.** 목적별로 나누되, 블록·연결·파라미터·HW/FW 분담·워크로드를 적은 기계가 읽는 **구조 기술** 하나에서 모든 모델의 설정이 나오게 한다. 목적별 모델의 약점인 일관성을 이것으로 막는다.

| 관점 | 모델과 추상화 | 기술 스택 | 속도 |
|---|---|---|---|
| 지연·처리량·꼬리 | 이산 사건, trace 기반. Decode와 NAND는 시간·확률 분포 | C++ 또는 Python 시뮬레이터 | 한 구성에 수십 분 |
| 전력 | 성능 모델의 블록별 활동률 × 상태별 전력 표 | 성능 모델에 얹음. 표는 이전 실리콘 측정과 합성 추정 | 성능과 함께 |
| 면적 | 모델이 아니라 표와 식. 기존 IP의 합성 실측 + 개수·깊이에 비례하는 추정 | 스프레드시트나 스크립트 | 즉시 |
| 기능, HW/FW 분담 | 블록 동작 모델. 고른 구조만 가상 플랫폼에서 실제 FW로 | C++ 동작 모델, SystemC/TLM(LT) | 수 초 ~ 수 시간 |
| 프로토콜, deadlock | 추상 상태 기계와 속성 | Formal tool | 수 분 |
| 블록 timing | 후보 공통 블록을 짧게 짜서 합성 | RTL | 수 시간 |

**묶어도 되는 것.** 성능과 전력은 한 모델로 본다. 활동률을 공유하고, 전력 한도가 성능을 제한하는 경우(열로 인한 속도 제한)에는 한 루프에서 봐야 하기 때문이다. 블록 동작 모델과 가상 플랫폼도 같은 C++ 코드를 쓴다. **묶지 말 것.** 성능 모델에 bit 단위의 decode 계산이나 실제 FW를 넣지 않는다. 넣는 순간 read 5천만 건을 돌릴 수 없다.

**통합이 필요한 순간.** 최종 후보에서 한 번, 모델을 합치지 않고 경계의 값을 맞춰 본다. ① 가상 플랫폼에서 실제 FW로 짧은 시나리오를 돌려 얻은 FW 왕복 시간과 단계별 지연이 성능 모델의 입력 분포 안에 있는가 ② 기능 모델의 요청·완료 순서가 성능 모델의 순서와 같은가 ③ Formal 모델의 중재 규칙이 성능 모델의 규칙과 같은가.

**에이전트가 맡는 일.** 구조 기술에서 각 모델의 설정과 코드를 만들고 갱신한다. 모든 결과에 구조 기술의 commit을 남기고, 다른 commit에서 나온 결과가 한 표에 실리지 않게 막는다. 교차 확인을 돌려 어긋난 곳을 보고한다. AX 관점에서 이 구성이 유리한 이유는 둘이다. 작은 모델은 에이전트가 고친 것을 사람이 확인할 수 있다. 그리고 모델 개수가 느는 유지 부담, 곧 목적별 구성의 실제 비용을 에이전트가 진다.

## 5. 예제: read 오류 복구 구조를 다시 정한다

### 5.1 요구사항 변화

```text
항목            이전 세대          이번 과제 (예시)
NAND            TLC                차세대 QLC
최대 용량       30.72 TB           122.88 TB
Host interface  PCIe Gen4          PCIe Gen5
전력 한도       25 W               25 W (그대로)
read 지연 기준  P99.99 ≤ 2 ms      P99.99 ≤ 2 ms
측정 조건       수명 말기 조건 없음  수명 말기 포함
오류 복구 제어  FW 순차 제어        ?
```

이전 세대는 read 오류 복구를 FW가 한 단계씩 제어했다. Decode 실패 interrupt를 받고, read 전압을 고르고, read를 다시 내보낸다. 단계마다 FW 왕복이 든다.

해석 모델 한 줄이 문제를 보여 준다. TLC에서는 soft decoding까지 가는 read가 10만 건에 2건(예시)이었다. 1만 건에 1건보다 드물어서 P99.99는 retry 경로가 정했고, FW 순차 제어로 충분했다. 차세대 QLC의 수명 말기에는 1만 건에 3건(예시)이다. 이제 **P99.99는 soft 경로의 지연이 정한다.** 용량이 네 배가 되면서 FW core는 mapping과 GC에 더 묶이고 FW 왕복의 꼬리도 길어진다.

단계별 시간으로 보면 이렇다(예시). 복구 한 단계는 NAND 재read 약 120 µs, 전송 약 40 µs, decode 약 8 µs다. FW 순차 제어에서는 여기에 FW 왕복이 붙는다. 중앙값은 수십 µs지만 FW core가 GC와 mapping으로 바쁠 때의 꼬리는 수백 µs다. Soft 단계는 read 전압을 바꿔 가며 추가로 읽고 soft decode를 돈다. 단계가 예닐곱 번 이어지는 read에서 FW 왕복의 꼬리가 한두 번만 겹쳐도 2 ms를 넘는다.

### 5.2 후보 구조

| 후보 | 한 줄 설명 | 블록도의 차이 |
|---|---|---|
| A. FW 순차 유지 | FW가 계속 제어. Read 전압 추적을 강화해 retry 횟수를 줄임 | 변경 없음. FW만 바뀜 |
| B. HW retry | Read retry만 HW로 옮김. Soft 단계는 FW 제어 | NAND interface에 retry FSM과 table. Decoder는 공유 |
| C. HW 복구 + soft 전용 경로 | Retry, soft read, soft decode를 HW(`rcv_ctrl`)가 제어. Soft decoder를 따로 둠 | `rcv_ctrl` 신규, soft LDPC 3기, 복구 요청 큐. FW는 정책·table·parity 복구 |
| D. 전부 soft 겸용 | Decoder 8기를 모두 soft 겸용으로 | Decoder 풀 확대. 제어는 C와 같음 |

RTL 설계자가 후보마다 추정을 붙인다. 기존 LDPC IP를 soft 전용 설정으로 다시 쓸 수 있는가, retry FSM이 NAND interface의 timing을 해치지 않는가, 면적은 얼마인가.

### 5.3 모델과 보정

모델 구성은 4.1의 권고를 따른다. 후보마다 구조 기술이 한 파일이고, 모델 다섯이 거기서 나온다.

```yaml
# arch/struct/rcv.arch.yaml · 구조 기술 (예시)
structure: C
blocks:
  nand_if:   {reuse: prev_gen, add: retry_fsm}
  hard_ldpc: {n: 8, reuse: prev_gen}
  rcv_ctrl:  {new: true, owner: hw}
  prio_q:    {depth: 64, order: "host 4 : gc 1"}
  soft_ldpc: {n: 3, reuse: ldpc_ip(soft)}
flow: [nand_if, hard_ldpc, rcv_ctrl, prio_q, soft_ldpc]
fw_role: [policy, retry_table, parity_recovery]
workload: [eol_mixed, gc_degraded]
```

```text
rcv.arch.yaml @ 4c1e9f2 에서 파생 (예시)
모델          답하는 것           스택           한 구성
perf (+전력)  P99.99 · 활동률     이산 사건 C++  약 20분
area          면적                표 + 식        즉시
func          요청 · 완료 규칙    C++ 동작 모델  수 초
vp            실제 FW · HSI 순서  SystemC/TLM    수 시간
formal        굶는 요청 없음      추상 모델+속성 수 분
불일치 검사   다섯 모델의 구조 commit 일치 · 통과
```

후보 넷을 가르는 것은 `perf` 와 `area` 다. `vp` 는 고른 구조에만 만든다. 아래는 `perf` 의 실행 설정과 보정 결과다.

```yaml
scenario: eol_mixed          # REQ-QOS-07 AC-1 (예시)
workload: {trace: dc_mixed_70r30w, qd: 64, reads: 5e7}
nand:
  type: qlc_next              # 초기 평가 lot 3종
  state: {pe: rated, retention: 3mo@40C}
  soft_entry_rate: 3e-4      # soft까지 가는 read
  retry_depth: dist/qlc_eol.csv
arch: arch/struct/rcv.arch.yaml   # 구조 기술에서 파생
structure: C                 # A | B | C | D
fw: {round_trip: dist/fw_rt_prev_gen.csv}
check: {p9999_ms: 1.78}      # 2 ms − 모델 오차 여유
```

```text
보정 · 이전 세대 실측 대 모델 (구조 A, TLC · 예시)
지표      실측       모델       오차
P50       92 µs      95 µs      +3%
P99       410 µs     431 µs     +5%
P99.99    1.38 ms    1.52 ms    +10%
믿는 범위  read 50~100% · QD ≤ 256 · 방치 ≤ 3개월
범위 밖    고온 방치 직후 전원 인가 (데이터 없음)
판정선     오차 여유 11% → P99.99 ≤ 1.78 ms
```

Read 5천만 건이면 P99.99 위의 표본이 5천 건이다. 본편 8장에서 제품 테스트가 잡은 문제(고온 방치 뒤 특정 lot의 지연 초과)가 바로 이 범위 밖에서 났다. 모델은 그 문제를 찾지 못했다.

### 5.4 여러 관점으로 돌린 결과

```text
구조 탐색 · eol_mixed · 216 구성 · 구조별 최선 (예시)
구조  P99.99    면적   전력   재사용  판정
A     3.41 ms   +0%    +0%    95%     지연 초과
B     2.27 ms   +3%    +1%    85%     지연 초과
C     1.52 ms   +14%   +5%    70%     통과
D     1.38 ms   +38%   +14%   55%     면적·전력 초과
제약  P99.99 ≤ 1.78 ms · 면적 ≤ +15% · 전력 ≤ +6%
면적·전력은 ECC·복구 블록 기준, 이전 세대 대비
```

| 관점 | A | B | C | D |
|---|---|---|---|---|
| FW 복잡도 | 복구 timing이 FW 스케줄링에 묶임 | Soft 단계 제어가 FW에 남음 | 정책·table·parity 복구만 | C와 같음 |
| 검증 가능성 | 지연은 emulation에서만 판정 | Retry는 sim, soft는 emulation | 요청 종료와 굶지 않음은 formal, 단계 지연은 sim | C와 같고 decoder 검증이 늘어남 |
| 리스크 | 전압 추적이 새 QLC에서 얼마나 맞을지 모름 | Soft 진입률이 오르면 무너짐 | 신규 블록 셋. HSI가 바뀜 | 전력 |

B가 탈락한 이유는 soft 단계다. Retry는 빨라졌지만 soft read와 soft decode는 여전히 FW가 제어하고 hard decode와 decoder를 나눠 쓴다. P99.99를 정하는 경로가 그대로 남았다. D는 지연이 가장 좋지만 soft 겸용 decoder 8기의 면적과 전력이 한도를 넘는다. 가중합으로 점수를 냈다면 D가 1등이 될 수도 있었다. C 안에서 제약을 통과한 구성은 9개였고(soft decoder 3~4기, 큐 깊이 32~128), 그중 면적이 가장 작은 것이 표의 C다.

A의 read 전압 추적은 버리지 않는다. Retry 횟수를 줄이는 FW 정책으로 C 위에 그대로 얹는다.

### 5.5 모델이 찾은 문제와 수정

C는 `eol_mixed` 를 통과했다. 에이전트가 나쁜 조건의 시나리오를 더 돌린다.

```text
시나리오 gc_degraded · 구조 C · soft_dec 3 (예시)
GC가 열화된 block을 읽는 구간
                  평상시      GC 구간
soft 요청 / 초    310         10,400
soft 큐 대기 P99  0.06 ms     1.9 ms
host P99.99       1.52 ms     2.61 ms  ← 기준 초과
원인  host 복구 요청이 GC 요청 뒤에 줄을 섬
수정  host 우선 큐 + GC 최소 처리량 (host 4 : GC 1)
재실행 host P99.99 1.63 ms · GC 처리량 −3%
```

Soft decoder 3기의 처리 용량은 초당 약 12,000건이다. 평상시에는 한가하지만 GC가 열화된 block을 읽으면 요청이 용량 가까이 몰린다. 우선 큐를 넣으면 반대로 GC가 굶을 수 있다. 이것은 성능 모델이 아니라 **formal 모델**로 본다. 큐와 중재 규칙을 추상 상태 기계로 적고 "모든 요청은 유한한 시간 안에 처리된다"를 증명한다. 이 속성은 그대로 RTL의 assertion이 된다.

### 5.7 RTL 설계자에게 넘어가는 것

```yaml
# arch/budget/BUD-RCV-001.yaml · jira: FEAT-330 (예시)
tail_path_ms:            # 합 1.66 + 여유 0.12 = 1.78
  host_ftl: 0.10
  first_read: 0.35       # die 대기 포함
  hw_retry: 0.51         # 3회 × 0.17
  soft_read: 0.30
  soft_queue: 0.15       # host 우선 큐의 대기 상한
  soft_decode: 0.25
blocks:                  # 면적 합 +14%
  rcv_ctrl:  {step_us: 2, area: "+1%", jira: FEAT-336}
  soft_ldpc: {n: 3, decode_us: 250, area: "+11%"}
  prio_q:    {depth: 64, area: "+2%", jira: FEAT-338}
```

```yaml
id: HSI-RCV-010            # 복구 요청 계약 (예시)
jira: FEAT-338
req: REQ-QOS-07
request: {tag, class: host | gc}
order: host 먼저. gc는 host 4건당 1건 이상
full: 큐가 차면 gc 요청부터 backpressure
bound: 모든 요청은 성공 또는 실패로 한 번 종료
fw_role: 정책과 retry table 설정, parity 복구
verify: [sva:a_host_first, sva:a_gc_no_starve]
```

예산표의 `tail_path_ms` 는 모델에서 P99.99 근처 read들의 경로를 구간별로 나눠 얻은 값이다. 구간의 합이 판정선 1.78 ms 안에 들어야 한다. 구간별 값은 블록의 수용 기준이 되고 Xray Test로 이어진다. 예를 들어 "rcv_ctrl의 단계 전환은 2 µs 안"은 시뮬레이션에서 cycle 수로 판정한다. P99.99 자체는 여전히 구조 모델, emulation, 제품 테스트에서 판정한다.

넘어가는 것은 셋이다. **블록별 예산**(2 ms를 꼬리 경로의 구간으로 나눈 값과 면적·전력), **interface 계약**(순서와 한계까지 적은 것), **microarchitecture의 출발점**(복구 단계의 상태, 큐 깊이, decoder 수). 예산을 어떻게 지킬지, 곧 FSM과 datapath와 pipeline은 RTL 설계자가 정한다.

### 5.8 같은 변경을 "RTL 먼저"로 했다면

```text
같은 변경, 두 경로 (예시 · 단계 기준)
단계            RTL 먼저            모델 먼저
구조 결정       회의에서 B 선택     A~D를 모델로 비교
RTL·블록 검증   B 구현, 기능 통과   C 구현, 예산 검사
P99.99 첫 확인  emulation (FW 포함) RTL 쓰기 전
지연 초과       emulation에서       모델에서 (A·B 탈락)
GC 경쟁         emulation 다음 회차 모델에서 (C 수정)
되돌아가는 범위 ECC·rcv_ctrl·HSI·   모델 설정과
                FW 복구·검증 환경   결정 기록
```

순서대로 적으면 이렇다. 회의에서 B를 고르는 것은 자연스럽다. 기존 RTL에서 가장 가깝다.

1. **구조 회의.** 평균 지연을 스프레드시트로 계산하면 B로 충분하다. Soft 진입률이 P99.99의 문턱을 넘었다는 사실은 평균에 묻힌다.
2. **RTL과 블록 검증.** Retry FSM을 NAND interface에 넣고 register와 C++ header를 고친다. 블록 검증은 기능과 "retry 재발행까지 몇 cycle"을 본다. 모두 통과한다. 이 단계의 속도는 실제로 빠르다.
3. **FW.** FW 담당이 새 header로 soft 단계의 제어를 구현한다. RTL과는 아직 만나지 않는다.
4. **Emulation.** RTL과 FW가 처음 함께 돈다. 수명 말기 NAND 모델로 혼합 부하를 걸면 P99.99가 기준을 넘는다. 원인이 HW인지 FW인지 가르는 데 시간이 든다. 원인은 어느 쪽의 bug도 아니고 구조다.
5. **되돌아감.** Soft 전용 경로와 `rcv_ctrl` 을 넣는다. ECC datapath, HSI, FW 복구 경로, testbench와 testplan이 다시 열린다. 면적도 다시 산정한다.
6. **다음 회차.** 고친 구조가 emulator에 다시 오른 뒤 GC 경쟁이 나온다. 이번에는 우선 큐 하나를 더하는 국소 수정이다.

단서도 적는다. B의 retry FSM과 그 검증 환경은 C에서도 대부분 쓴다. 경험 많은 아키텍트가 처음부터 C를 골랐다면 첫 번째 되돌아감은 없다. 그래도 GC 경쟁은 emulation에서 나온다. 그리고 변경이 retry table 확장뿐이었다면 RTL 먼저가 옳다.

## 6. RTL 설계자에게 달라지는 것

- **구조 단계에 들어간다.** 후보의 구현 가능성, 면적·timing 추정, 재사용 판단을 낸다. 이 추정이 모델의 입력이다. 추정은 구조 결정 이슈의 댓글로 남긴다.

```text
RTL 리드  11-03  FEAT-330 댓글 (예시)
후보 C 구현 추정
  soft LDPC   기존 IP를 soft 전용 설정으로 재사용.
              1기당 ECC 블록의 약 +3.7% (±1%)
              근거: 이전 과제 합성 결과
  rcv_ctrl    신규. FSM 5 상태, 약 +1%
  retry FSM   nand_if의 command 경로에 삽입.
              timing 영향은 짧게 짜서 합성해 확인
  재사용      hard LDPC·nand_if datapath 그대로
```
- **받는 것이 바뀐다.** 블록도와 서술 문서가 아니라 예산표, 계약, 실행해 볼 수 있는 모델을 받는다.
- **RTL 단계에서 예산과 대조된다.** Commit마다 블록 지연(시뮬레이션의 cycle 수), 면적, 전력(합성 추정)이 예산과 비교된다.
- **구조로 되돌려 보낼 수 있다.** 본편 4장의 경우다.

```text
MR !2207  FEAT-352 soft 경로 · 예산 검사 (예시)
항목                예산      측정      판정
rcv_ctrl 단계 전환  2 µs      1.4 µs    통과
soft decode (최대)  250 µs    236 µs    통과
ECC 블록 면적       +15%      +17%      초과
→ 구조 모델 재실행: soft_dec 3 → 2
  host P99.99 1.74 ms (판정선 1.78) · 통과
  GC 구간 처리량 −21% · 지속 쓰기 요구 충족
→ ADR-RCV-003 개정 2 · 승인 대기 (아키텍트)
```

예산 초과가 "RTL을 더 다듬어라"로만 끝나지 않는다는 점이 다르다. 초과의 원인이 구조에 있으면 RTL 설계자가 구조 결정 이슈에 댓글로 올리고, 에이전트가 대안을 모델로 돌리고, 아키텍트가 결정 기록을 개정한다. 모델이 있으면 이 왕복은 RTL을 다시 짜 보지 않고 끝난다.

| 줄어드는 일 | 늘어나는 일 |
|---|---|
| 구조 문서를 해석해 의도를 추측하는 일 | 구조 단계의 면적·timing 추정 |
| 구조 문제로 인한 후반의 큰 재작업 | 예산을 지키는 microarchitecture 결정 |
| 후반에 한꺼번에 받는 PPA 결과 | 예산 초과의 원인 판단, 구조에 올리는 변경 요청 |
| Interface 문서의 수작업 동기화 | Interface 계약과 블록 수용 기준 정의 |

## 7. 모델과 RTL의 정합을 지키는 방법

모델은 구조를 고른 뒤에 버려지기 쉽다. 계속 쓰게 만드는 장치가 여섯이다.

1. **구조 기술이 원본.** 큐 깊이, decoder 수, retry 최대 횟수는 구조 기술(4.1) 한 파일에 있고 모든 모델의 설정과 RTL parameter가 거기서 나온다. 한쪽만 바꾸는 일이 생기지 않는다. 공개 사례에서는 성능 모델과 RTL이 instruction decode table을 공유한다(벤더 기고, CPU 대상).
2. **예산 검사.** 6장의 commit별 비교다. 초과하면 모델에 실제 값을 넣고 다시 돌린다.
3. **같은 자극의 교차 실행.** 모델이 낸 블록 수준의 요청 순서를 RTL testbench에 다시 넣고 완료 순서와 지연 분포를 비교한다. TLM 모델과 RTL의 성능 차이를 같은 자극으로 비교하는 방법은 DVCon 논문에 있다(검색 요약만 확인).
4. **Formal 속성의 승계.** 구조 단계에서 증명한 속성이 RTL assertion이 되고, RTL이 구조 모델의 가정을 지키는지 확인한다. Architectural formal verification의 세 번째 단계다.
5. **실측으로 재보정.** RTL과 FW가 emulator에 오르면 측정 분포로 모델을 다시 맞추고 차이를 기록한다. 모델이 틀렸던 곳의 기록은 다음 과제의 "믿는 범위"가 된다.
6. **소유와 독립.** 구조 모델과 판정선은 아키텍트 소유다. 구조 모델은 성능 예산의 기준이고, 기능의 reference model은 검증 엔지니어가 따로 소유한다. 같은 에이전트가 모델과 RTL을 같은 해석으로 만들면 둘이 같이 틀리고 서로 맞는다. 그래서 모델을 만든 에이전트와 RTL을 만드는 에이전트의 작업과 권한을 나눈다.

구조 모델의 P99.99는 설계 검증 기록이다. 퀄 증빙이 아니다.

| 모델이 틀린다 | 보정 오차와 범위를 적고 판정선에 여유를 둔다. Emulation과 제품 테스트로 다시 판정한다 |
| 모델 과신 | "범위 밖" 조건을 결정 기록에 적는다. 결정의 전제를 적고 깨지면 다시 연다 |
| 에이전트가 모델을 결과에 맞춘다 | 보정에 쓰지 않은 실측으로 확인한다. 판정선과 시나리오는 사람 소유다 |
| 탐색이 끝나지 않는다 | 기간과 실행 예산을 정한다. 제약을 통과한 후보가 나오면 멈춘다 |
| 모델이 방치돼 RTL과 어긋난다 | 7장의 예산 검사와 재보정 |

**지키는 선.**

- 구조의 선택과 책임은 사람에게 있다. 에이전트는 후보와 근거를 내고, `FEAT-330` 의 승인 전환은 사람만 한다.
- 모델은 적어 둔 범위 안에서만 믿는다.
- 판정은 모델 실행의 출력으로 한다. 에이전트의 요약으로 하지 않는다.
- 작은 변경에 모델을 강요하지 않는다. 2장의 기준으로 가른다.

**확인하지 못한 것.**

- SSD 컨트롤러의 구조 탐색이나 HW/FW 분담을 에이전트로 한 공개 사례는 없다.
- 에이전트가 성능 모델의 구축·보정 시간을 얼마나 줄이는지 잰 독립 자료는 없다. 2장의 "손익분기점 이동"은 방향에 대한 주장이다.
- 구조 문제를 늦게 발견했을 때의 비용 배수는 인용하지 않았다. 검색에 나온 수치(IBS 2018)는 원문을 확인하지 못했다.
- 통합 모델과 목적별 모델을 같은 설계에서 비교한 자료는 찾지 못했다. 4.1의 권고는 위 사례들과 속도·검증의 논리에 근거한 판단이다. 구조 기술에서 여러 모델을 파생하는 구성을 SSD 컨트롤러에 쓴 공개 사례도 없다.
- 상용 가상 플랫폼 제품에 SSD 컨트롤러용 모델이 있는지 확인하지 못했다.

**팀 확인이 필요한 가정.**

| 가정 | 확인할 것 |
|---|---|
| 이전 세대는 read 오류 복구를 FW가 순차 제어했다 | 실제 분담. 이미 일부가 HW라면 후보 A·B의 출발점이 달라진다 |
| 이전 세대의 성능 모델이 있고 고쳐 쓸 수 있다 | 모델의 형태(스프레드시트, 이산 사건, SystemC)와 보정 이력. 지금 모델이 통합형인지 목적별인지 |
| 모델별 실행 시간(약 20분, 수 시간)과 스택 | 팀의 기존 도구와 서버 환경. 예시일 뿐이다 |
| 이전 제품에서 단계별 지연과 FW 왕복 시간을 뽑을 수 있다 | 로그와 telemetry의 항목 |
