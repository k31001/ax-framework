# 전환 5. 문화: 개인 요령 → 측정 · 공유 · 학습

> 상태: 초안 (2026-11-11). 상세 영상 `shift5` 의 원본이다.
> 예제의 팀, 파일 이름, 수치(95분, 41개 중 6개 등)는 흐름을 보여 주기 위한 예시다. 실제 측정값이 아니다.

## 1. 한 줄 요약

"AI를 쓰니 빨라진 것 같다"는 느낌을, **기준선 · 지표 쌍 · playbook · 실패 기록**이라는 네 가지 남는 것으로 바꾼다. 문화는 구호가 아니라 팀이 매주 반복하는 일과 저장소에 쌓이는 파일이다.

## 2. 지금 무엇이 문제인가

검증 팀의 아침을 보자. 야간 regression 결과가 나와 있고, 두 사람이 실패 로그를 열어 분류한다.

- **요령이 개인에게 있다.** 로그 요약을 잘 뽑는 사람의 프롬프트는 그 사람의 메모장과 개인 폴더에 있다. 옆자리 사람은 같은 시행착오를 처음부터 다시 한다. 그 사람이 과제를 옮기면 요령도 같이 나간다.
- **재지 않는다.** 아침 triage에 몇 분이 드는지, 묶음을 잘못 지은 것이 몇 건인지 아무도 모른다. 그래서 AI를 붙인 뒤에 나아졌는지도 말할 수 없다. 남는 것은 "빨라진 것 같다"는 인상이다.
- **실패가 사라진다.** 에이전트가 원인이 다른 실패를 한 묶음으로 합쳐 반나절을 날린 일은 당사자가 조용히 고치고 지나간다. 다음 주에 다른 사람이 같은 곳에서 넘어진다.
- **느낌과 지표가 어긋난다.** 공개 자료가 같은 격차를 보여 준다. McKinsey 2026 설문에서 응답자의 80%가 개인 생산성 향상을 말했지만 EBIT 기여를 말한 곳은 37%였다(검색 요약 기준). Faros AI의 텔레메트리(개발자 22,000명, 자사 발표)에서는 개발자당 작업 처리량이 33.7% 늘 때 첫 리뷰까지의 대기 시간이 156.6%, 개발자당 버그가 54% 늘었다. Faros는 개발자의 체감이 하류에서 측정된 결과보다 늦게 따라온다고 적었다. 처리량 하나만 보면 좋아진 것으로 읽힌다.

이 축이 빠지면 나머지 네 전환도 검증할 수 없다. 스펙을 실행 가능하게 바꾸고 루프를 닫았는데 그것이 나아진 것인지 판단할 근거가 없기 때문이다.

## 3. 전환 후의 모습

같은 아침이다. 달라지는 것은 다섯 가지다.

1. **기준선이 먼저 있다.** 에이전트를 붙이기 전에 지금 값을 잰다. 대상은 regression triage 시간, 스펙 변경에서 검증 완료까지의 시간, 리뷰 대기 시간, bug escape(시뮬레이션에서 잡혔어야 하는데 emulation·FPGA 이후에 나온 bug)다.
2. **속도 지표는 품질 guardrail과 쌍으로 본다.** triage 시간은 오분류율과, 스펙 변경 → 검증 완료 시간은 bug escape와, 리뷰 대기는 리뷰 없이 반영된 변경 비율과 짝을 짓는다. DORA도 소프트웨어 delivery 지표 다섯 개를 throughput 셋과 instability 둘로 나누고, 지표 하나만 보지 말고 서로 긴장 관계에 있는 여러 지표를 쓰라고 안내한다.
3. **잘 된 방법은 팀 자산이다.** 작업 지시서 양식, 에이전트 playbook, 평가 세트를 git 저장소에 두고 코드처럼 리뷰한다. 요령을 고치려면 PR을 올린다.
4. **실패를 기록하고 나눈다.** 에이전트가 틀린 사례는 정해진 양식으로 한 건씩 남고, 그 입력과 정답이 평가 세트의 문제가 된다. Playbook을 고칠 때마다 이 문제들을 다시 돌린다.
5. **평가와 육성이 역할 변화를 따라간다.** 기여로 인정하는 것이 작성량에서 통과 기준 정의, 판단의 질, 팀 자산 기여(playbook PR, 평가 문제 추가, 실패 기록)로 옮겨간다. 주니어에게는 에이전트의 가설을 보기 전에 직접 debug하는 구간을 남겨 둔다.

## 4. 실제 예제: 한 팀의 4주

본편 S5-4의 장면(야간 regression 실패 312건을 에이전트가 원인 4개로 묶음)을 그 팀이 **어떻게 도입했는가**로 확대한다. 블록은 오류 복구 제어 블록 하나, 참여자는 검증 엔지니어 둘과 설계자 하나다.

### 전: 남는 것이 없다

```text
~/notes/prompt_log_요약.txt     ← 한 사람의 개인 폴더
(메신저) "어제 에이전트가 묶음을 잘못 지어서 오전을 날렸어요"
(주간 회의) "AI 쓰니까 triage가 좀 빨라진 것 같습니다"
```

### 1주: 바꾸지 않고 잰다

실험 카드를 먼저 쓴다. 속도 지표, guardrail, 중단 조건을 결과를 보기 전에 정해 둔다.

```yaml
# experiments/triage-agent.yaml  (예시)
hypothesis: 에이전트가 1차 묶음과 원인 가설 초안을 내면
            아침 triage 시간이 준다
scope: 오류 복구 제어 블록, 야간 regression
speed_metric: triage 소요 (분/일)
guardrail:
  - 오분류율 = 사람이 나중에 고친 묶음 / 전체 묶음
  - 신규 실패를 기존 묶음에 넣어 놓친 건수 = 0
stop_if: guardrail이 기준선보다 나쁜 채 2주 지속
unit: 팀 단위 집계. 개인별 값은 수집하지 않음
```

기준선은 야간 regression 10회로 잰다. 배정까지의 시간과 오분류는 regression DB와 티켓 이력에서 자동으로 뽑는다. 사람이 쓴 분(分)은 로그에 없으므로 이 기간에만 하루 한 줄씩 직접 적는다.

```text
# metrics/triage-baseline.md  (예시, 야간 regression 10회)
아침 triage 소요         평균 95분/일 (2명 합계)
실패 → 담당 배정         중앙값 3.5시간
오분류                   묶음 41개 중 6개 (15%)
  └ 사람이 나중에 쪼개거나 원인 범주를 바꾼 묶음
```

### 2주: 작은 실험, 실패를 적는다

에이전트가 스크립트의 1차 묶음을 받아 대표 seed를 재실행하고 원인 가설을 붙인다. 수요일에 틀린다. Scoreboard의 오류 문구가 같다는 이유로 원인이 다른 실패 둘을 한 묶음으로 합쳤고, 설계자가 티켓을 검토하다 찾아낸다. 이 일이 기록 한 건이 된다.

```yaml
# failures/F-007.yaml  (예시)
workflow: regression-triage
what: 원인이 다른 실패 2종을 한 묶음으로 합침
why: UVM_ERROR 문구가 같음 (scoreboard: data mismatch)
     A는 RTL FSM의 완료 누락, B는 TB sequence의 대기 누락
found_by: 설계자의 티켓 검토 (묶음 재분류)
cost: B의 담당 배정이 반나절 늦어짐
fix: playbooks/regression-triage.md 규칙 4 추가
eval_case: evals/triage/case-023
# 양식에 "누구 탓" 칸은 없다
```

### 3주: 주간 공유에서 팀 자산으로 굳힌다

```text
주간 AI 공유 (30분, 3주차)   (예시)
1. 지표 쌍                  5분   triage 시간 / 오분류율
2. 이번 주 실패 기록        10분  F-007, F-009
3. playbook 변경 리뷰       10분  PR "규칙 4 추가"
4. 다음 주 실험 한 가지     5분
```

Playbook은 PR로 고치고 동료가 리뷰한다. 병합 조건은 평가 세트 점수가 떨어지지 않는 것이다.

```diff
# playbooks/regression-triage.md  (예시)
  1. error signature로 1차 묶음 (기존 스크립트)
  2. 묶음마다 대표 seed 1개를 파형과 함께 재실행
  3. 원인 가설에는 로그 줄과 파형 구간을 붙인다
+ 4. 문구가 같아도 첫 불일치 시점의 FSM 상태가
+    다르면 묶음을 나눈다              (F-007)
  하지 않는 것: 티켓 종결, 근거 없는 "TB 문제" 분류
```

평가 세트는 과거 실패 로그와 사람이 확정한 정답(어느 묶음인지, 원인 범주가 RTL·TB·환경 중 무엇인지)의 쌍이다. F-007의 로그 둘은 `case-023` 이 되고 정답은 "서로 다른 묶음"이다.

```text
$ make eval-triage      # playbook PR마다 실행  (예시)
case-001 … case-022   pass 19 / fail 3
case-023 (F-007)      fail → 규칙 4 적용 후 pass
묶음 정확도  19/23 → 21/23
```

### 4주: 지표 쌍을 보고 결정한다

```text
# metrics/triage-week4.md  (예시)
                  기준선        4주차
triage 소요       95분/일   →   40분/일    (2주차 55분)
오분류율          6/41 15%  →   4/38 11%   (2주차 9/40)
신규 실패 누락    —             0건
결정: 인접 블록 하나로 확대. 중단 조건은 그대로.
```

2주차에는 시간이 이미 줄었지만 오분류는 9건으로 늘었다. 시간만 봤다면 그 주에 성공으로 보고했을 것이다. 쌍으로 봤기 때문에 확대를 미뤘고, 실패 기록이 playbook을 고쳤고, 그다음에 guardrail이 기준선 아래로 내려왔다. 표본이 작으므로 이 차이는 추세로만 읽고, 확대한 뒤에도 같은 쌍을 계속 본다.

## 5. 전환 전략

1. **기준선 측정.** 재지 않은 것은 나아졌다고 말할 수 없다. 대기열이 쌓이는 워크플로 하나만 고른다(전략 문서의 순서 원칙: 측정이 자율보다 먼저).
2. **지표 쌍과 중단 조건의 사전 합의.** 결과를 본 뒤에 기준을 정하면 좋은 숫자만 고르게 된다.
3. **되돌릴 수 있는 워크플로 하나에서 작은 실험.** Triage는 틀려도 사람이 고칠 수 있다. 실패는 그 자리에서 한 건씩 기록한다.
4. **주간 공유로 굳히기.** 실패 기록을 playbook 규칙과 평가 문제로 바꾼다. 이 단계가 없으면 3번의 배움이 다시 개인에게 남는다.
5. **확대 또는 중단, 그리고 평가·육성 반영.** 쌍이 모두 나아질 때만 넓힌다. 여러 워크플로에서 자산이 쌓인 뒤에 인정 기준과 육성 방식을 바꾼다. 순서를 뒤집어 평가부터 바꾸면 숫자를 맞추는 행동이 먼저 나온다.

## 6. 실행 계획

| 단계 | 누가 | 만드는 것 | 완료 판단 |
|---|---|---|---|
| 기준선 | 워크플로 담당 엔지니어, 인프라 담당 | 지표 정의서, regression DB·티켓 이력에서 값을 뽑는 스크립트, 기준선 카드 | 같은 스크립트를 다시 돌려 같은 값이 나온다. 팀이 정의에 동의했다 |
| 사전 합의 | 팀 리더, 담당 엔지니어 | 실험 카드(속도 지표, guardrail, 중단 조건, 집계 단위) | 결과를 보기 전에 저장소에 올라가 있다 |
| 작은 실험 | 엔지니어 2~3명 | 실패 기록, playbook 초판 | 실패 기록이 0건이 아니다(0건이면 기록이 안 되고 있다는 신호) |
| 공유 정례화 | 진행자는 돌아가며 맡음 | 주간 공유 안건, playbook PR, 평가 세트 | 실패 기록마다 playbook 변경이나 평가 문제가 연결돼 있다. Playbook 변경이 평가 점수와 함께 리뷰된다 |
| 확대·중단 | 팀 리더 | 지표 쌍 비교와 결정 기록 | 결정이 사전 합의한 조건에 따라 내려졌다 |
| 평가·육성 | 팀 리더, 인사 담당, 시니어 | 기여 인정 항목, 주니어의 직접 debug 구간 운영 규칙 | 면담에서 playbook·평가 세트·실패 기록 기여가 실제로 언급된다 |

주니어의 직접 debug 구간은 이렇게 운영할 수 있다. 일주일에 묶음 하나는 에이전트의 원인 가설을 가린 채 먼저 직접 debug하고, 끝난 뒤 가설과 비교한다. 차이가 나면 그것이 실패 기록이나 평가 문제의 후보다.

## 7. 기술 요소

| 요소 | 내용 | 성숙도 |
|---|---|---|
| 지표 수집 | Regression DB(실패 수, 묶음, 완료 시각), 티켓 시스템(배정 시각, 재분류 이력), 리뷰 도구(요청·첫 응답 시각), 에이전트 실행 로그(token, 재시도)에서 스크립트로 추출 | 원천 시스템은 상용. 추출과 지표 정의는 직접 구축 |
| 지표 화면 | 속도 지표와 guardrail을 한 카드에 나란히. 팀·워크플로 단위만 표시 | 대시보드 도구는 오픈소스·상용. 카드 구성은 직접 |
| Playbook·평가 세트 저장소 | git 저장소 하나. `playbooks/`, `evals/`, `failures/`, `experiments/`, `metrics/` | 상용(기존 형상관리 그대로) |
| 평가 실행기 | Playbook PR마다 평가 세트를 돌려 점수를 PR에 붙임 | CI는 상용. Triage용 채점기와 정답은 직접 구축 |
| 실패 기록 양식 | YAML 한 장. 무엇이, 왜, 누가 찾았나(역할), 비용, 고친 곳, 평가 문제 | 직접(양식뿐이라 가벼움) |
| 주간 공유의 틀 | 30분, 고정 안건 4개 | 도구 불필요 |

평가 세트로 triage 품질을 재는 방식에는 공개 선례가 있다. Samsung의 DVCon U.S. 2026 논문은 통제된 150건 benchmark로 담당자 배정 정확도를 쟀다(기존 방식 28.7% → 76.7%, 자사 논문).

## 8. 리스크와 지키는 선

| 리스크 | 지키는 선 |
|---|---|
| 지표가 개인 감시가 된다 | 팀·워크플로 단위로만 집계한다. 개인별 사용량 순위를 만들지 않는다. 실험 카드에 집계 단위를 적는다 |
| 지표가 목표가 되어 숫자를 맞춘다 | 목표 수치는 기준선 뒤에 정하고, 단일 지표를 목표로 걸지 않는다. DORA 안내서도 Goodhart의 법칙을 들어 같은 경고를 한다 |
| 실패 보고가 불이익이 된다 | 양식에 사람 이름 칸을 두지 않는다. 실패 기록과 평가 문제 추가를 기여로 인정한다. Google SRE의 blameless postmortem이 같은 원리다("처벌이 두려우면 사람들은 문제를 드러내지 않는다") |
| 측정 없이 도입만 민다 | 기준선과 실험 카드가 없는 워크플로는 확대 대상에 올리지 않는다 |
| 과의존과 역량 공동화 | 주니어의 직접 debug 구간, 가설을 받기 전에 먼저 풀고 비교하기. Anthropic의 무작위 대조 실험(52명)에서 AI 사용 그룹의 이해도 점수는 50%, 직접 작성 그룹은 67%였고 격차는 debugging 문항에서 가장 컸다. 코드를 받은 뒤 이해를 확인하는 질문을 한 사용자는 높은 점수를 유지했다 |
| 공유가 자랑 발표회가 된다 | 안건 순서를 지표 쌍과 실패 기록부터로 고정한다 |
| 측정 자체가 부담이 된다 | 자동으로 뽑히는 값부터 쓴다. 손으로 적는 값은 기준선 기간에만 받는다 |
